### Рекомендация [В, уверенность низкая–средняя]

По ревью: B конфликтует с «замороженной» security-зоной SEC-003 и активным API-004; E для *демо* почти равна по рискам, не трогая security-ядро. Решение «C или E» не должно зависеть от одного эксперимента на одном домене; универсальное ядро честнее выделять **после двух реальных доменов**.

**B — с обязательным «воротами решения» после эксперимента HX-1**: если HX-1 подтверждает, что новый домен подключается без правки ядра за пределами согласованных швов, — рассматривать C (вынос); если опровергает, — вернуться к решению между E (честно признать HERMES набором шаблонов) и D. Альтернатива D **не рекомендуется сейчас**: нет доказательства, что инварианты и 934 теста дешевле переписать, чем параметризовать. Альтернатива E — легитимный запасной вариант, если **коммерческий срок демо важнее архитектурного тезиса**; её цена — отказ от тезиса «один оркестратор» на этапе демо.

## 3. Минимальный архитектурный эксперимент HX-1 (Deliverable G)

**Форма:** отдельная ветка/worktree от `main`; **не** вмешивается в активные Stories; ничего не коммитится в `main` до решения владельца. Без платных LLM-вызовов (fake/replay), без новых зависимостей (либо с явным согласованием).

### 3.1 Утверждения и критерии (бинарные, заданы заранее)

| № | Утверждение директивы | Конструкция проверки | Опровергается, если |
|---|---|---|---|
| 1 | Ядро обслуживает более одного домена | Dispatcher (синтетический) запущен тем же `SupportAgent`-циклом | правка `agent.py`, `tool_executor.py`, `authorization.py` **вне перечня, зафиксированного до старта поимённо (файл, функция, максимум строк diff)**. «Этапы конвейера» как шов признан неопровергаемым (`_start` содержит `_classify`/`_evaluate_refund`), поэтому перечень обязателен. Один домен тем же автором — **индикация, не доказательство** |
| 2 | Возможности подключаются независимо | Dispatcher добавлен без правок файлов SupportOps-домена (`git diff` по ним пуст) | требуется правка `policy.py`/`refund_*`/`tools.py` |
| 3 | Разные tenants — разные наборы возможностей | tenant-ecom и tenant-prop; вызов чужой возможности → `TOOL_NOT_ALLOWED`; **плюс** корпус инъекций в данных tenant с целевой метрикой | gate пропускает недоступный tool (критический провал). **Ограничение:** скриптовый fake-LLM проверяет лишь детерминированный Gate; устойчивость реальной модели к инъекциям не измеряется |
| 4 | Модули общаются через контролируемые контракты | Dispatcher получает данные об объекте через `PropertyRegistry` порт, передача между шагами типизирована | модуль обращается к данным другого напрямую / через глобальное состояние |
| 5 | Границы безопасности сохраняются | **Основной:** tenant-инварианты, написанные ДО реализации (A не видит/не меняет данные B; чужое = несуществующее; идентичность — пара `(tenant, customer)`). **Необходимый, но недостаточный:** 934 существующих теста (не знают о tenant: зелёные = нет регрессии, не безопасность композиции) | любой tenant-инвариант красный или существующий security-тест красный из-за смены поведения |
| 6 | Трудоёмкость следующих решений снижается | Измерить фактические часы и число затронутых файлов: добавление первого домена (Dispatcher), затем тривиальной третьей возможности | третья возможность требует сопоставимых затрат с первой — утверждение не подтверждено. **n мал: подтверждение — только индикация** |

### 3.2 Состав работ

1. **Швы** (4–8 дн.): реестр как параметр; `ExecutionContext`+tenant и доверенный конструктор; порт данных; этапы конвейера как список; вынос sanitization (опционально).
2. **Dispatcher-домен, синтетика** (5–10 дн.): `PropertyRegistry`, `MaintenanceRequest` (+ конечный автомат, ключ идемпотентности = ID события), `UrgencyPolicy` на таблице регламентов (синтетической, помеченной как таковая), `ContractorRouting` (детерминированный), `HumanTask`-заглушка (запись в таблицу, без UI).
3. **Тесты** (3–5 дн.): tenant-изоляция, подмена инструмента скриптом LLM, идемпотентность повторного события, fail-closed классификатор, регрессия.
4. **Мост сервиса** (5–10 дн., можно отложить): воркер claim/lease поверх `runs` + `POST /v1/tickets` — **зависит от решения владельца об источнике `customer_id`** и от работы другой сессии (api004-http).

Итого **≈ 17–33 дня** для HX-1 с мостом, **≈ 12–23** без моста — **нижняя граница при отсутствии блокеров**. Ревью: швы занижены (порт данных вместо `mock_data` затрагивает большую часть 934 тестов; реестр глобален; Harness нужно влить и переработать; не заложены схема сущностей/событий пути II, security-ревью, согласование с API-004); реалистичная верхняя граница может быть вдвое выше. Допущения: один разработчик + ИИ; PostgreSQL доступен; Email и реальные интеграции исключены; регламенты синтетические. Уверенность — **низкая**; пересмотреть после шагов 1–2.

### 3.3 Что НЕ доказывает HX-1

Качество работы реальной LLM на неисправностях (нужен Live-evaluation, в `main` не реализован), надёжность email-канала, юридическую приемлемость, окупаемость, пригодность для STC.

## 4. Первый демонстрационный AI Dispatcher

### Реалистичная форма [Г]

Сценарная демонстрация на синтетическом tenant «property»: обращение (REST/симулятор чата) → классификация неисправности → вопрос об недостающих данных (состояние сущности «ожидает уточнения») → ответ → срочность по регламенту → заявка → маршрутизация исполнителю → эскалация (создание HumanTask). Результаты — таблицы и trace без ПД.

### Что мешает уже сегодня [Ф]

1. Нет Dispatcher-домена, порта данных, tenant-связки в ядре.
2. Нет воркера и `POST /v1/tickets` (последний ждёт решения владельца).
3. Нет Human Task и канала уведомлений.
4. Evaluation Harness не в `main`; Live-evaluation не реализован — **качество классификации реальной моделью не измерено**.
5. Все данные — только синтетика; реальный запуск требует отдельного compliance review (решение API-003 D-8).

### Оценка Time to First Commercial Demo

**Одним числом не оценивается.** Порядок 4–8 недель — только нижняя граница при отсутствии блокеров (решение по `customer_id`, воркер, Harness) **[Н, низкая]**; при альтернативе E — короче, ценой тезиса. Коммерческая ценность демо зависит от недоступных в репозитории данных: **регламентов срочности реального заказчика** и перечня исполнителей.

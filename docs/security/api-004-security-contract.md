## 1. Threat Model

**Защищаемые активы:** (A1) данные заказов и клиентов tenant; (A2) изоляция между tenant; (A3) API-ключи и секрет сервера (pepper); (A4) целостность решений по возврату (`RefundPolicyEngine`, Gate); (A5) trace и логи как канал утечки.

**Модель нарушителя:** внешний нарушитель без ключа; владелец валидного ключа tenant X, атакующий tenant Y; утёкший/отозванный ключ; недоверенный текст тикета и вывод LLM (prompt injection); читатель логов/БД без доступа к pepper.

| # | Угроза | Вектор | Контроль (раздел) |
|---|---|---|---|
| T1 | Подбор ключа | Перебор секрета | Секрет 256 бит; единый 401; rate limit на неуспехи (WP-9) (§3, §7) |
| T2 | Перебор/перечисление prefix | Различимость «prefix неизвестен» vs «хэш неверен» | Единый ответ; выравнивание времени фиктивной проверкой (§3.4) |
| T3 | Timing-oracle сравнения | Побайтовое сравнение | `hmac.compare_digest` над HMAC-значениями (§3.3) |
| T4 | Подмена tenant | `tenant_id` в теле, заголовке, query, path | Источник только credential; `extra=forbid`; заголовки не читаются (§4.2) |
| T5 | IDOR / доступ к чужому объекту | Угадывание `ticket_id`/`run_id` | Tenant-фильтр в каждом запросе; единый 404 (§5) |
| T6 | Различимость чужого и несуществующего | Код/тело/время ответа | Один код, одно тело, один путь выполнения (§5, I-4) |
| T7 | Эскалация через scope | Использование `tickets:read` для записи | Scope проверяется до разбора тела и до обращения к объекту (§3.6) |
| T8 | Prompt injection → чужой tenant/клиент | Текст тикета просит «покажи заказы клиента Z» | Tenant и customer не входят в схему tool-call; задаются исполнителем (§2, I-1, I-2) |
| T9 | Утечка секретов через ошибки/логи | Исключения, 422, трассировка | Закрытый набор кодов, 422 без input, ключ не логируется (§7, I-6) |
| T10 | Утечка PII через trace | Произвольные поля в trace | Типизированная metadata-only структура (§5.4, I-7) |
| T11 | Использование отозванного ключа | Кэш, гонка отзыва | Нет кэша аутентификации в MVP; проверка `revoked_at` на каждом запросе (§6, I-10) |
| T12 | Компрометация БД | Дамп `api_credentials` | В БД только HMAC; pepper вне БД; ротация pepper (§3.3, §6) |
| T13 | Расширение полномочий worker | LLM заставляет worker действовать от другого tenant | Worker берёт tenant из строки run, не из вывода LLM; credential worker не получает (§2, I-8) |
| T14 | Утечка во внешний LLM в Demo | Случайный сетевой клиент | Demo не создаёт клиентов; тест-страж сокетов (I-9) |
| T15 | Кража ключа из URL/логов прокси | Ключ в query string | Принимается только `Authorization: Bearer`; query-ключи не поддерживаются (§3.2) |
| T16 | Кросс-tenant идемпотентность | Одинаковый `Idempotency-Key` | Область ключа — tenant; 409 только внутри tenant (§5.3) |
| T17 | Инъекция в заголовки/логи | `X-Request-ID` | Валидация `[A-Za-z0-9-]{1,64}` (Beta, WP1) |

**Вне модели (явно):** компрометация доверенного кода, хоста или секрета pepper; компрометация backend tenant (он авторитет по своим `customer_id`, см. §2); DDoS на сетевом уровне; юридические вопросы D-8.

## 2. Trust Boundaries

```text
Internet ──TLS──▶ [API: FastAPI] ──▶ [PostgreSQL] ◀── [Worker] ──▶ [SupportAgent] ──▶ [LLM]
  недоверен       TB1/TB2: ключ→tenant   TB7        TB10         TB5/TB6        недоверен
```

| Граница | Доверенный вход | Недоверенный вход | Правило |
|---|---|---|---|
| Клиент → API (TB1/TB2) | Только результат поиска credential в БД | Заголовки, тело, path, query | `tenant_id`/scopes — только из credential. Любое «tenant» от клиента игнорируется или отклоняется |
| `customer_id` (TB3) | Значение от аутентифицированного backend tenant, зафиксированное в `tickets` | — | Неизменяем после вставки; в прогон попадает только из сохранённого тикета |
| API → БД (TB7) | `TenantContext.tenant_id` | — | Репозиторий не имеет метода без `tenant_id` |
| Worker ← БД (TB10) | Строка `runs`/`tickets` (tenant, customer, ticket) | Текст `message` | Worker **не аутентифицируется ключом и не имеет scopes**; его полномочия — это содержимое строки run. Worker не вызывает API |
| Worker → Agent | `trusted_customer_id`, `trusted_ticket_id`, tenant-привязанный порт данных | Текст тикета | Новый `SupportAgent` и новый порт на каждый run (одно tenant на экземпляр) |
| Agent ↔ LLM (TB5) | — | Весь вывод LLM, включая tool-call | Gate, `ToolCall`-валидация, перекрытие идентичности исполнителем (SEC-003 G4) |
| Tools → данные (TB6) | Порт, созданный с `tenant_id` при сборке run | Аргументы tool-call | `tenant_id` **не является аргументом** ни одного tool и не присутствует в JSON-схеме tool-ов |
| Egress (TB8) | Закрытые коды, metadata-only trace | Всё остальное | Нет текста исключений, тел сообщений, ключей |

Ключевое следствие: **LLM не может выбрать tenant или клиента, потому что у него нет параметра, через который это можно выразить.** Это структурный, а не фильтрационный контроль.

Принятое допущение (унаследовано от D-2/D-4): backend tenant — авторитет для собственных `customer_id`. Компрометация ключа tenant даёт доступ ко всем клиентам **этого** tenant — но не к другим.

## 3. Authentication Contract

### 3.1 Формат credential

```text
sok1.<prefix>.<secret>
sok1      версия формата (позволяет сменить схему без неоднозначности)
prefix    12 символов [a-z2-7] (base32, 60 бит, случайный, уникальный) — идентификатор для поиска, не секрет
secret    43 символа base64url без паддинга (256 бит из os.urandom / secrets)
```

- Генерация — только `secrets`/`os.urandom`; ни prefix, ни secret не выводятся из tenant/времени.
- Строгая проверка формата **до** обращения к БД: полное совпадение с regex, длина заголовка ≤ 128 байт. Несоответствие — тот же 401 (не 400).
- Передача — только `Authorization: Bearer <key>`. Ключ в query/path/теле/cookie не принимается и не логируется.
- Ключ показывается один раз при выдаче. Восстановить его невозможно.

### 3.2 Разбор заголовка

Любой из случаев → единый 401 (§7): заголовок отсутствует; схема не `Bearer` (регистр схемы нормализуется); пустой токен; несколько заголовков `Authorization`; формат не совпал; лишние пробелы/управляющие символы.

### 3.3 Проверка секрета и хранение verifier

```text
key_hash = HMAC-SHA256(pepper[pepper_id], "sok1." + prefix + "." + secret)     # 32 байта
verify   = hmac.compare_digest(computed, record.key_hash)
```

- **Почему HMAC, а не Argon2/bcrypt:** секрет имеет 256 бит энтропии, подбор нереалистичен; медленный KDF не добавляет защиты, но создаёт DoS-вектор (каждый запрос с неверным ключом стоит CPU). Pepper защищает от сценария «дамп БД без окружения» и от ошибочно выданных ключей низкой энтропии.
- Pepper: ≥ 32 байт, из окружения/секрет-хранилища, **не в репозитории и не в БД**; версионируется `pepper_id` (§6.4).
- Сравнение — только `hmac.compare_digest`. Прямое `==` над секретом или хэшем запрещено (проверяется статическим тестом).
- В БД хранится: `credential_id`, `tenant_id`, `key_prefix`, `key_hash`, `pepper_id`, `scopes`, `created_at`, `expires_at?`, `revoked_at?`, `last_used_at?`. Сам ключ — никогда.

### 3.4 Алгоритм аутентификации (нормативный порядок)

1. Разобрать и проверить формат (§3.1–3.2). Неудача → шаг 6.
2. `record = repo.get_by_prefix(prefix)`.
3. Если `record is None`: выполнить **фиктивную** проверку (`compare_digest` против константного значения с реальным HMAC-вычислением) — выровнять стоимость. Далее шаг 6.
4. Вычислить HMAC и сравнить в константное время. Неудача → шаг 6.
5. Проверить `revoked_at is None`, `expires_at` не истёк (время — из инжектируемых часов), `tenant` не отключён. Любое нарушение → шаг 6. Иначе → построить `TenantContext` и вернуть.
6. Поднять единую `Unauthenticated`. Внутренняя причина фиксируется **только** в серверном аудите (§7.3), не в ответе.

Уточнения редакции 2 (проверены тестами):

- Запись из репозитория считается **недоверенными данными**: неверные типы, `key_hash` не 32 байта, `key_prefix` не равен запрошенному, неизвестный `pepper_id`, naive `expires_at`, невалидные `tenant_id`/`credential_id` → тот же 401 (`bad_record`). Для неизвестного `pepper_id` и некорректной записи выполняется фиктивная проверка (как в шаге 3).
- Любое исключение репозитория при `get_by_prefix` → `503 service_unavailable` (текст исключения отбрасывается); при `touch_last_used` → игнорируется, решение не меняется.
- `revoked_at is not None` отзывает ключ независимо от значения (даже будущего); истёк, если `now >= expires_at`.
- **Отложено на M02:** проверка «tenant не отключён» (шаг 5) не реализована — у `CredentialRecord` нет статуса tenant; до таблицы `tenants` отключение = отзыв всех credential (§6.7). Найдено независимым ревью (MEDIUM-2).
- Кэш проверенного контекста между `SecuredRoute` и зависимостью хранится в отдельном ключе ASGI-scope конкретного запроса, не в `scope["state"]` (MEDIUM-1 ревью).
- Порядок «HMAC → revoked → expired» сохранён: отзыв/истечение проверяются только после успешной проверки секрета.

Различие между «неизвестный prefix», «неверный хэш», «отозван», «истёк» наружу не передаётся ни в теле, ни в заголовках, ни по коду. Выравнивание времени — best-effort; абсолютной гарантии по времени контракт не даёт (см. Open Questions).

### 3.5 Единый ответ 401

Статус `401`, тело `{"error":{"code":"unauthenticated","message":"<фикс. текст>","request_id":"…"}}`, заголовок `WWW-Authenticate: Bearer`. Байтовое равенство тела и заголовков (кроме `request_id`) для всех причин — проверяется тестом.

### 3.6 Scope: поведение при отсутствии или недействительности

- Scopes — закрытое множество (`StrEnum`): `tickets:write`, `tickets:read`, `trace:read`. Неизвестная строка scope в записи credential при загрузке отбрасывается и считается отсутствием права (fail-closed); запись такого значения при выдаче запрещена.
- Порядок проверок (согласован с Beta §11.0): **аутентификация (401) → scope (403) → заголовки/размер/валидация → операция**. FastAPI разбирает тело **до** зависимостей (проверено: битый JSON без ключа даёт 422), поэтому порядок гарантируется классом маршрута `SecuredRoute` (`security/dependencies.py`), который аутентифицирует и проверяет scope до чтения тела; без него зависимости остаются защитой, но порядок ошибок нарушается (I-13/AC-5). Scope проверяется по маршруту и credential **до** любого обращения к объекту и до разбора тела, поэтому `403` не зависит от существования объекта и не раскрывает его.
- Нехватка scope → `403 insufficient_scope` с фиксированным текстом; ответ **не перечисляет** имеющиеся или требуемые scopes.
- Пустой набор scopes = credential, который аутентифицируется, но ничего не может.
- `trace:read` по умолчанию не выдаётся. Пока маршрут trace не зарегистрирован (до WP-8), запрос получает стандартный 404 приложения, а не 403.

### 3.7 Границы доверия между API, worker и агентом

- **API** аутентифицирует, авторизует, пишет `tickets`/`runs` с `tenant_id` из `TenantContext`. Не исполняет агента.
- **Worker** не принимает HTTP-запросов, не хранит и не использует API-ключи, не имеет scopes. Читает run по `run_id`, берёт `tenant_id`/`customer_id`/`ticket_id` из строки. Пишет результат с fencing по `attempt`.
- **Агент** получает только `trusted_customer_id`, `trusted_ticket_id` и порт данных, уже привязанный к tenant. Не видит credential, pepper, `TenantContext`.
- **LLM** не получает ни одного из перечисленных значений как управляемый параметр.

## 4. TenantContext

### 4.1 Контракт

```python
@dataclass(frozen=True, slots=True)
class TenantContext:
    tenant_id: str                 # slug, из credential
    credential_id: str             # для аудита и отзыва; не секрет
    scopes: frozenset[Scope]       # закрытое множество; из credential
```

Намеренно **отсутствуют**: сам ключ/prefix/hash, `customer_id` (принадлежит тикету, не сессии), `request_id` (контекст запроса), роли, флаги «admin/superuser», произвольный `dict`.

Свойства:

- Неизменяем; hash/eq по значению; `__repr__` не содержит секретов (их там нет по построению).
- Создаётся **только** функцией `authenticate` после успешной проверки (§3.4). Конструктор не вызывается из кода обработчиков; не является Pydantic-моделью запроса и не может быть заполнен из JSON/заголовков (проверяется тестом: попытка передать `tenant_id` в теле → 422, значение игнорируется).
- Не сериализуется в ответы и не пишется в логи целиком — только `credential_id` и `tenant_id`.
- `tenant_id` валидируется как slug (`[a-z0-9][a-z0-9-]{0,62}`); значение не из этого набора → отказ создания контекста (fail-closed).

### 4.2 Источники

| Атрибут | Единственный источник | Запрещённые источники |
|---|---|---|
| `tenant_id` | `api_credentials.tenant_id` найденной и проверенной записи | тело, query, path, `X-Tenant-Id` и любые заголовки, вывод LLM, значение по умолчанию |
| `scopes` | `api_credentials.scopes` (после фильтра по закрытому множеству) | то же; запрос «повысить scope» не существует |
| `credential_id` | `api_credentials.credential_id` | — |

Заголовок `X-Tenant-Id` не читается вообще (не «читается и игнорируется»), чтобы нельзя было получить расхождение двух путей.

### 4.3 Передача в repository

- Методы API-репозиториев принимают `tenant_id: str` **keyword-only, без значения по умолчанию**; единственное место, откуда берётся значение, — `ctx.tenant_id`. Метода «найти тикет по id без tenant» не существует.
- Все SQL — вида `WHERE tenant_id = :t AND <object_id> = :id`; `INSERT` берёт `tenant_id` из аргумента, не из DTO запроса. DTO запроса не имеет поля `tenant_id` (`extra=forbid`).
- Репозиторий не принимает `TenantContext` целиком: scopes — забота слоя зависимостей, а не хранилища (меньше связность; worker использует те же репозитории без `TenantContext`).
- Worker использует отдельный путь: чтение run по `run_id` без tenant-фильтра **разрешено только в worker-репозитории** (иначе не узнать tenant), с немедленной фиксацией tenant из строки и последующими запросами только с ним. Этот метод не доступен из API-слоя (разные Protocol-ы; проверяется тестом на импорты).
- RLS в БД — второй эшелон, не замена кодового контроля.

### 4.4 Доступ к чужим объектам

Чужой, несуществующий и синтаксически некорректный идентификатор → один и тот же `404 not_found` (§5, I-4). Различимости по коду, телу, заголовкам и (best-effort) времени быть не должно.

## 5. Authorization Invariants

Каждый инвариант формулирован проверяемо. «Тест» — минимальная форма проверки для `tests/service/security/**`.

| ID | Инвариант | Как проверяется |
|---|---|---|
| **I-1** | Tenant не выбирается моделью. `tenant_id` отсутствует в схемах tool-call и в аргументах tools; порт данных создан с tenant при сборке run | Тест: JSON-схемы tools не содержат `tenant`; tool-call с `tenant_id` отклоняется валидацией; в Demo с подделанным tool-call данные другого tenant недоступны |
| **I-2** | Customer identity не выбирается моделью. `customer_id` — только из сохранённого тикета (наследует SEC-003 G1/G4) | Регрессия SEC-003 + тест через HTTP: текст тикета «я клиент C2» не меняет доступ |
| **I-3** | Любое обращение к tenant-scoped данным содержит проверку принадлежности | Статический тест: все публичные методы API-репозиториев имеют обязательный `tenant_id`; интеграционный тест на двух tenant для каждого эндпоинта |
| **I-4** | Чужой и несуществующий объект неразличимы | Тест: один и тот же ответ (статус, тело, заголовки, кроме `request_id`) для чужого, несуществующего и некорректного id |
| **I-5** | Отказ авторизации не раскрывает существование объекта | Scope-проверка предшествует поиску объекта; тест: 403 на существующий и несуществующий id идентичен |
| **I-6** | Ошибки не раскрывают секреты (ключи, pepper, хэши, текст исключений, SQL, пути) | Инъекция исключений с маркерной строкой в каждый слой → маркера нет в теле/логах; 422 без input |
| **I-7** | Trace не содержит произвольных пользовательских данных | Ответ trace строится из типизированной структуры с закрытыми полями; тест с маркерами в `message`/tool output (расширение SEC-003 G8) |
| **I-8** | Worker не получает дополнительных полномочий через LLM | Тест: вывод LLM со ссылками на другой tenant/ticket/run не меняет контекст; worker не имеет доступа к credential-репозиторию (разделение Protocol-ов) |
| **I-9** | Demo Mode не обращается к внешним LLM | Тест-страж `socket.connect`; в Demo не создаётся клиент LLM; Live без явной конфигурации не стартует |
| **I-10** | Отзыв credential исключает новые авторизованные запросы | Тест: запрос → отзыв → следующий запрос 401 немедленно (без TTL-кэша) |
| **I-11** | Единый 401 для всех причин отказа аутентификации | Параметризованный тест по 8+ причинам: идентичные статус/тело/заголовки |
| **I-12** | Ключ и pepper не попадают в логи, ответы, исключения, `repr` | Тест с перехватом логов; статический запрет `==` над секретами |
| **I-13** | Аутентификация предшествует разбору тела | Тест: невалидное тело без ключа → 401, не 422 |

### 5.3 Идемпотентность и tenant

`UNIQUE (tenant_id, idempotency_key)`: одинаковый ключ у разных tenant независим; `409 idempotency_key_reuse` возможен только внутри tenant и не раскрывает чужие ключи.

### 5.4 Trace

Маршрут не регистрируется до WP-8. Ответ — только поля из закрытого списка (Beta §11.3); каждое чтение пишется в `audit_events`; доступ требует `trace:read` и tenant-фильтр; чужой/несуществующий `run_id` → единый 404.

## 6. Credential Lifecycle

### 6.1 Выдача

Оператор запускает скрипт (в MVP админ-API нет): генерируется ключ (§3.1), вычисляется `key_hash`, в БД пишется запись, ключ печатается **один раз** в stdout и нигде не сохраняется. Запись скриптом фиксируется в аудите (кто, когда, `credential_id`, scopes; без ключа).

### 6.2 Принцип наименьших прав

Ключ выдаётся с минимальным набором scopes. Один ключ — одно назначение (backend, который создаёт тикеты: `tickets:write`; читатель статусов: `tickets:read`). `trace:read` — отдельный ключ с обоснованием.

### 6.3 Ротация ключей

Допускается несколько активных credential у одного tenant. Процедура: выдать новый → перевести клиента → убедиться по `last_used_at`, что старый не используется → отозвать старый. Без простоя. Рекомендованный максимальный срок жизни — вопрос владельцу (§10); поле `expires_at` предусмотрено.

### 6.4 Ротация pepper

`pepper_id` в записи. Окно миграции: сервер знает старый и новый pepper; проверка идёт по `record.pepper_id`. Перехэширование возможно только в момент успешной аутентификации (секрет известен) — либо выдачей новых ключей. После окна старый pepper удаляется; оставшиеся на нём ключи перестают работать (ожидаемое поведение, документируется).

**Реализация (ред. 3):** `SUPPORTOPS_PEPPER` + `SUPPORTOPS_PEPPER_ID` — активный pepper; `SUPPORTOPS_PREVIOUS_PEPPERS` (`id=value,id=value`) — retained, **только проверка**. Формат **утверждён владельцем (D3)**; повторяющиеся `pepper_id` запрещены; предыдущие pepper используются только для проверки существующих credential. `PepperSet.from_config` отвергает дубликаты, совпадение id активного pepper, слишком короткие значения; сообщение об ошибке фиксировано и не содержит значений (`ServiceConfigurationError`, старт отменяется). Pepper, снятый из конфигурации, → 401 для его ключей (fail-closed). `repr` настроек не раскрывает значения. Перехэширование при входе **не** реализовано (MVP).

### 6.4a AuthenticationGate

Ограничивает число одновременных проверок credential (каждая занимает поток threadpool и соединение PG): `max_concurrent_authentications` (по умолчанию **3**, решение владельца по ревью M2), ожидание `auth_queue_wait_seconds` (1.0 с), параметры `create_app`. Сначала дешёвая проверка формата заголовка в event loop (мусор не занимает поток), затем семафор. Насыщение → `503 service_unavailable` + `Retry-After: 1` (единственный 503 с этим заголовком), запрос **не** допускается без аутентификации. `/healthz` не использует gate и остаётся доступным при насыщении (тест I7). Gate — **ограничитель параллелизма, не rate limit** (§7.4); `async def` сам по себе защитой от перегрузки не считается. Семафор создаётся на каждый event loop отдельно (ревью M1). **M2 (закрыт):** при общем пуле PostgreSQL требуется `max_concurrent_authentications < pool.max_size` (по умолчанию 3 < 4, так что одно соединение остаётся свободным). Размер пула берётся из `create_app(pool_max_size=…)` либо из репозитория (`PostgresCredentialRepository.pool_max_size` ← `DatabasePool.max_size`). Проверка выполняется при старте: нарушение или значение `< 1` → `ServiceConfigurationError("Invalid authentication gate configuration.")` (текст фиксирован, значения не раскрываются). Если размер пула **неизвестен**, лимит работает лишь как ограничитель параллелизма: `gate.pool_isolation_verified` равно `False`, в лог пишется предупреждение, ресурсная изоляция **не заявляется**. Тесты: `tests/service/security/test_auth_gate_pool_limit.py`, `tests/integration/test_m2_gate_pool_pg.py` (пул ровно из 4 соединений, 150 одновременных неизвестных ключей + одновременное создание тикетов, два event loop).

Ограничения MVP: gate per-process (не распределённый); это **не** rate limit и **не** полноценная защита от DoS — внешнего rate limit нет (D5); production readiness не заявляется. Gate не защищает пул от нагрузки, не проходящей через аутентификацию.

### 6.5 Отзыв

`UPDATE api_credentials SET revoked_at = now()` (единственная разрешённая мутация, кроме `last_used_at`). Проверка `revoked_at` — на **каждом** запросе, читающем запись из БД. **Кэширование результатов аутентификации в MVP запрещено**; если оно понадобится (нагрузка), TTL и допустимое окно задерживающего отзыва — отдельное решение владельца и новый инвариант.

Поведение для уже принятых работ: отзыв ключа не отменяет принятый run (авторизация произошла при приёме), но результат нельзя получить отозванным ключом. Альтернатива — вопрос владельцу.

### 6.6 Компрометация

Отозвать ключ → выдать новый → просмотреть аудит по `credential_id`. При подозрении на компрометацию pepper — ротация pepper и перевыпуск всех ключей.

### 6.7 Отключение tenant

В MVP один Demo Tenant; отдельная таблица `tenants` добавляется аддитивно со вторым tenant. До этого отключение = отзыв всех его credential.

## 7. Failure Semantics

### 7.1 Таблица ответов

| Ситуация | Статус | `error.code` | Что раскрывается |
|---|---|---|---|
| Нет/искажён/неизвестный/отозванный/истёкший ключ | 401 | `unauthenticated` | Ничего о причине. `WWW-Authenticate: Bearer` |
| Нет нужного scope | 403 | `insufficient_scope` | Ничего о существовании объекта, о наборе scopes |
| Чужой / несуществующий / некорректный id | 404 | `not_found` | Идентично во всех трёх случаях |
| Tenant/служебные поля в теле | 422 | `validation_error` | Путь и тип поля без значения |
| Тело/заголовок невалидны | 400/413/415/422 | по Beta §11.1 | Без input |
| Повтор идемпотентного ключа с другим телом | 409 | `idempotency_key_reuse` | Только в своём tenant |
| БД недоступна (`StorageUnavailable`, ошибка `get_by_prefix`) | 503 | `service_unavailable` | Без причин, без `Retry-After`. **Не** трактуется как успех аутентификации |
| Насыщение AuthenticationGate | 503 | `service_unavailable` | `Retry-After: 1` |
| `StorageFailure`, `InvalidRepositoryInput` (ошибка БД не-доступности / программная ошибка) | 500 | `internal_error` | Фиксированный текст; в лог — только имя класса. *Решение владельца D1 (INTEGRATION-GATE-01): `StorageFailure` → 500 `internal_error`; `StorageUnavailable` → 503 `service_unavailable` (D2)* |
| Неожиданное исключение | 500 | `internal_error` | Фиксированный текст, без трассировки |

### 7.2 Fail-closed правила

- Любая ошибка в цепочке authenticate → 401 или 503, **никогда** «пропустить». Недоступность БД при проверке ключа → 503, не 401 (клиенту важно отличить сбой сервиса) и не разрешение.
- Любая ошибка при построении `TenantContext` → отказ запроса.
- Неизвестное значение scope/tenant/формата → отказ.

### 7.3 Серверный аудит и логи

Логируются: `request_id`, маршрут, результат (`ok`/`denied`), **категория внутренней причины** (`bad_format`, `unknown_prefix`, `bad_secret`, `revoked`, `expired`, `scope`), `credential_id` и `tenant_id` — только если запись найдена. Не логируются: ключ, secret, prefix, пришедший от неаутентифицированного клиента (управляемая атакующим строка → риск log injection/раскрытия опечаток ключа), тело, заголовок `Authorization`.

### 7.4 Rate limit (WP-9)

Лимит неуспешных аутентификаций по источнику; ответ `429` + `Retry-After` не должен позволять отличить причины неуспеха. До WP-9 перебор нереалистичен из-за 256 бит, но DoS через дорогие ответы остаётся: аутентификация должна быть дешёвой (HMAC, один индексный запрос).

## 8. Integration Interfaces

Исходный набор — из Beta (`api-004-m01-wp1-api-skeleton.md` §6), здесь уточнён. Все изменения общих интерфейсов — только по согласованию обеих сторон до M02.

```python
# src/supportops_service/interfaces.py   (владелец файла — Beta; изменения — с подтверждением Alpha)
class Scope(StrEnum):
    TICKETS_WRITE = "tickets:write"
    TICKETS_READ  = "tickets:read"
    TRACE_READ    = "trace:read"

@dataclass(frozen=True, slots=True)
class TenantContext: tenant_id: str; credential_id: str; scopes: frozenset[Scope]

@dataclass(frozen=True, slots=True)
class CredentialRecord:
    credential_id: str; tenant_id: str; key_prefix: str
    key_hash: bytes; pepper_id: str; scopes: frozenset[str]   # сырые строки: фильтр по Scope — в Alpha
    expires_at: datetime | None; revoked_at: datetime | None

class CredentialRepository(Protocol):
    def get_by_prefix(self, key_prefix: str) -> CredentialRecord | None: ...
    def touch_last_used(self, credential_id: str) -> None: ...   # best-effort, не влияет на решение

class Clock(Protocol):
    def now(self) -> datetime: ...                                # инжектируется для тестов expiry
```

```python
# Alpha: src/supportops_service/security/dependencies.py
def authenticate(...) -> TenantContext                  # FastAPI-зависимость; единый 401
def require_scope(scope: Scope) -> Callable[..., TenantContext]   # 403 insufficient_scope
```

**Что Alpha ждёт от Beta:**

1. Envelope ошибок и коды `unauthenticated`, `insufficient_scope`, `not_found`, `internal_error` в `errors.py`; возможность добавить заголовок `WWW-Authenticate` к 401 через публичную точку расширения.
2. Публичные точки подключения роутеров/зависимостей без правки `app.py` Alpha-ом.
3. Репозитории `tickets`/`runs` с обязательным `tenant_id` keyword-only; отдельный worker-Protocol для чтения run без tenant.
4. Конфигурация: `pepper` и `pepper_id` из окружения (`ServiceSettings`), без значений по умолчанию; приложение не стартует без них, если подключена аутентификация.
5. Фабрика приложения без чтения окружения при импорте; инжектируемые `CredentialRepository` и `Clock` (для in-memory fake в тестах).
6. Обработчик 422 без отражения input; запрет `X-Tenant-Id` не требует поддержки — заголовок просто не читается.
7. Порт данных для tools (`OrderDataPort`), создаваемый с `tenant_id` на каждый run; запрет исполнения для tenant, кроме `demo`.

**Что Alpha даёт Beta:** `authenticate`/`require_scope`, in-memory `CredentialRepository`-fake, PG-реализацию `repositories/credentials.py`, набор security-тестов (`tests/service/security/**`).

**Реализация (ред. 3, интеграция):** 401/403/503-аутентификации формирует **только** Alpha `SecurityError` (`security/errors.py`, поверх `errors.error_body`). Общий `errors.py` выровнен на канонические коды (`401 unauthenticated`, `403 insufficient_scope`, `503 service_unavailable`, `409 idempotency_key_reuse`) для постороннего `HTTPException` и добавляет обработчики `StorageUnavailable`→503, `IdempotencyConflict`→409, `StorageFailure`/`InvalidRepositoryInput`→500. `Scope`, `TenantContext`, `CredentialRecord`, `CredentialRepository`, `Clock` определены **один раз** — в `interfaces.py`; `security/contracts.py` удалён (статический тест).

**FastAPI-интеграция (`create_app`):** `create_app(settings, *, credentials, clock, v1_routers, max_concurrent_authentications, auth_queue_wait_seconds)`; `redirect_slashes=False`; `/v1`-роутеры монтируются только вместе с `CredentialRepository` и pepper, иначе старт отменяется. На старте выполняются `find_unsecured_routes` и `find_scopes_outside_route_signature`; нарушение → `ServiceConfigurationError`, приложение не стартует. Router-level scope dependencies для защищённых `/v1` запрещены (scope объявляется в сигнатуре маршрута).

**PostgreSQL `CredentialRepository`:** `repositories/credentials.py` (`PostgresCredentialRepository`) поверх `DatabasePool` Beta; константный параметризованный SQL, префикс валидируется до запроса, любой сбой → `CredentialStoreError` с фиксированным текстом (без цепочки `__context__`) → 503; `touch_last_used` троттлится (60 с) и не влияет на решение. Проверено на PostgreSQL 16 (`tests/security_pg`, `tests/integration`). Ограничение: `repositories/credentials.py` — единственный модуль repositories, которому разрешено обращаться к `api_credentials`.

**Ограничения MVP (актуально на ред. 3):** нет проверки отключения tenant (нет таблицы `tenants`); нет rate limit (WP-9) и распределённого gate; нет кэша аутентификации (намеренно); `touch_last_used` — запись в БД на горячем пути (троттлится); перехэширование при смене pepper отсутствует; сроки жизни ключей и выдача — вне пакета; роли БД (`supportops_worker`, least privilege) не созданы (WP4).

**Разделение владения** — по Beta §6; Alpha не правит `app.py`, `errors.py`, `interfaces.py`, `pyproject.toml`; Beta не правит `security/**`. Расхождение документов: Beta относит `TenantContext` к `interfaces.py` (Beta) и одновременно перечисляет `security/tenant_context.py` за Alpha. Решение (предложение, ждёт Beta): определение — только в `interfaces.py`; `tenant_context.py` содержит фабрику/валидацию. Реализовано так, проверено статическим тестом.

## 10. Open Questions

Решения владельца / согласования с Beta:

1. **403 vs 404 для `trace:read`.** Контракт: 403 `insufficient_scope` (согласовано с Beta §11.0). Альтернатива — отвечать 404, скрывая сам факт существования маршрута для ключей без права. Что выбираем после WP-8?
2. **Срок жизни ключей и обязательность ротации.** Максимальный `expires_at` по умолчанию (например 90/180 дней) или бессрочные с ручной ротацией в MVP?
3. **Поведение уже принятых run при отзыве ключа.** Контракт: run завершается, результат недоступен отозванному ключу. Альтернатива — отмена run.
4. **Кэш аутентификации.** Запрещён в MVP (I-10). Допустим ли короткий TTL (например 30 с) при росте нагрузки и с каким документированным окном отзыва?
5. **Выравнивание времени.** Контракт — best-effort (фиктивная проверка). Нужна ли жёсткая гарантия и измерения, или это принятый остаточный риск?
6. **Место определения `TenantContext`.** Предложено: только `interfaces.py`; фабрика в `security/tenant_context.py` (реализовано). Требует подтверждения Beta до M02.
7. **Репозиторий принимает `tenant_id: str` или `TenantContext`.** Контракт — `str` (проще для worker и тестов). Подтвердить с Beta.
8. **Один prefix = один credential, `UNIQUE`.** Достаточно ли 60 бит prefix против коллизий и перечисления, или удлинить?
9. **Хранение pepper.** Окружение (MVP) vs секрет-хранилище. Кто отвечает за ротацию?
10. **Аудит неуспешных аутентификаций.** Достаточно структурированных логов или нужна таблица `audit_events` для auth-событий (объём, retention — связь с D-8)?
11. **Rate limit (WP-9).** Единица лимита: IP, prefix, tenant? Prefix нельзя использовать до успешной аутентификации без риска DoS на чужой ключ.
12. **Как tenant попадает в агент без изменения `src/supportops_agent/**`.** Контракт предполагает порт данных, созданный с tenant на run. Если это окажется невозможным без правки Authorization Gate или `tool_executor`, это затрагивает утверждённые инварианты SEC-003 — требует остановки и решения владельца.
13. **Логирование prefix.** Контракт запрещает логировать prefix неаутентифицированного запроса. Подтвердить, что операционная диагностика этим не пострадает.

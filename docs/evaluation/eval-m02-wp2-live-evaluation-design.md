# EVAL-M02/WP2 — Live LLM Evaluation: дизайн

**Статус:** проект. Не реализован, не утверждён владельцем. Самостоятельный архитектурный документ.
**Реализация перенесена** на E2-Phase 08 — Outcome Intelligence (HERMES Epoch II). В E2-Phase 01 не выполняются: реальные LLM-вызовы,
интеграция платных провайдеров, live budget enforcement. Отсутствие реализации Live Evaluation не блокирует интеграцию Deterministic Harness и Record & Replay.
**База:** `eval/supportops-eval-001` @ `3bcdfb9` (EVAL-M02/WP1: Record & Replay).
**Ограничение:** документ не меняет `src/**`, SupportAgent, MONOLITH и Coordinatorium. Реальные LLM-вызовы при проектировании не выполнялись.

Цель — расширить **существующий** Evaluation Harness так, чтобы можно было измерять качество реальной модели, не смешивая это с проверкой агентной логики. Новая платформа, второй Runner или второй датасет не создаются.

## 0. Исходные факты (проверены по коду)

| Факт | Следствие для дизайна |
|---|---|
| `SupportAgent(client, classifier)` получает оба источника LLM через конструктор (DI). | Подмена источника возможна **без изменений SupportAgent**: нужны обёртки вокруг `client` и `classifier`. |
| LLM-цикл использует `client.responses.create(...)` и цепочку `previous_response_id`. | `store` отключить нельзя (цепочка требует хранения на стороне провайдера) → защита данных держится на «только синтетика», а не на `store=false`. |
| Классификатор — отдельный контракт: `TicketClassifier.classify(ticket) -> ClassificationResult`, внутри `OpenAITicketClassifier` вызывает `client.responses.parse(model, instructions, input, text_format)`. | Классификатор не покрыт записью WP1 и в Live-режиме должен проходить через тот же контроль бюджета. |
| В Fake/Replay `classification_accuracy` и `tool_selection_accuracy` определяются **скриптом**, а не моделью. | Те же формулы в Live означают качество модели. Метрики обязаны быть разведены по пространствам имён (см. §1.3). |
| `usage` в fake фиксирован (10/5/15), задержек и стоимости в harness нет. | Latency, токены и стоимость измеряются **обёрткой клиента**, а не агентом. |
| `scripts/eval_classification.py` — ручной live-smoke на 10 обращениях, читает `.env`, **без бюджетного контроля**. | Это уже существующий «второй путь» к платной LLM. WP2 не копирует его и не расширяет (решение D-6). |
| SDK `openai` по-прежнему импортируется `agent.py` (M7). | Дизайн не обещает «процесс без SDK»; обещает «нет клиента, нет сети» там, где это так. |
| Runner исполняет каждый сценарий внутри `_isolated` → `_no_network`; любая попытка соединения = `V_NETWORK` (`runner.py:81-130`). | Live несовместим с текущей изоляцией без явного исключения для транспорта клиента (§3.2). |
| Модель агента прошита константой `MODEL_NAME` (`agent.py:46`, используется в `_call_model`, `agent.py:882`); модель классификатора — параметр конструктора. | Выбор модели возможен только как явный override запроса в обёртке (§3.2, `request_overrides`). |
| `_compare` требует `result.llm_calls == len(llm_script)` (`runner.py:191-204`), `llm_calls = client.responses.calls` считает только `create`. | Для Live нужны правки Runner (§3.5). |
| Агент ведёт цепочку `previous_response_id`: исходящий `input` содержит только `tool_outputs`, реальный контекст хранится на стороне провайдера; шагов до `MAX_AGENT_STEPS=10`. | Оценка стоимости по исходящему `input` занижает расход (§3.3). |
| SDK `openai` по умолчанию повторяет запросы при ошибках (`max_retries=2`). | Скрытые повторы обходят счётчик бюджета. Live-клиент обязан создаваться с `max_retries=0` (см. §3.2). |

## 1. Три класса проверки

### 1.1. Определения

| | A. Deterministic Fake | B. Recorded Replay | C. Live LLM |
|---|---|---|---|
| `Mode` | `deterministic_fake` | `recorded_replay` | `live_evaluation` (новый) |
| Источник ответов | скрипт датасета | запись | реальная модель |
| Что измеряет | корректность агентной логики | воспроизводимость логики на зафиксированных ответах | **качество ответов модели** в рамках агента |
| Детерминизм | полный | полный (байт-в-байт) | нет |
| Сеть / платные вызовы | нет | нет | да, только по разрешению и в бюджете |
| `evaluation_class` в отчёте | `agent_logic` | `agent_logic` | `live_model` |
| `model_quality_claim` | `false` | `false` | `true` только для завершённого прогона (см. §3.4) |

Replay, записанный из Live-ответов (будущая опция `--record-live`), остаётся классом `agent_logic` с `recording_origin: live_model`: он замораживает ответы модели и проверяет агента, но не оценивает новую версию модели.

### 1.2. Правило не смешивать

1. Отчёт содержит `mode`, `evaluation_class`, `recording_origin` (`synthetic_fake` | `live_model` | `n/a`). Все три обязательны; отсутствие любого — ошибка загрузки отчёта.
2. Инструменты анализа (сводки, `compare`) **отказываются** принимать отчёты разных `evaluation_class` в одном вызове.
3. Агрегированных «общих» оценок нет: ни среднего между режимами, ни единого score.
4. `summarize()` печатает класс и режим в первой строке; метрики Live печатаются с префиксом `live.`.

### 1.3. Пространства имён метрик

Метрики WP1 переименовываются в отчётах в `logic.*` (`logic.classification_accuracy`, …) — их смысл «агентная логика на заданных ответах» не меняется. В Live-отчётах присутствуют только `live.*`. Один и тот же ключ в двух режимах невозможен, поэтому ошибочно сопоставить числа нельзя. Это изменение схемы отчёта (версия отчёта 2) и входит в WP2-C; ожидаемые **значения** шести метрик WP1 не меняются.

## 2. Классификатор: запись и воспроизведение (WP2-A)

### 2.1. Где подключаться

Рассмотрены два уровня.

| Вариант | Плюсы | Минусы |
|---|---|---|
| (a) Уровень протокола `TicketClassifier.classify` → `ClassificationResult` | Симметричен `FakeClassifier`; не нужен импорт исключений SDK в replay; нет зависимости от формы `responses.parse` | Не видит фактические kwargs `responses.parse`; дрейф ловится только по публичным константам |
| (b) Уровень `client.responses.parse` | Реальный `OpenAITicketClassifier` исполняется и в replay (ловит дрейф его кода) | Replay должен бросать `openai.OpenAIError` и воспроизводить внутренний формат `ParsedResponse` (жёсткая привязка к SDK; SDK в процессе и так присутствует через `classification.py`, поэтому довод не про «наличие импорта», а про связанность) |

**Рекомендация: (a)**, с fingerprint из публичных констант (§2.3). Остаточный риск: изменение внутренних kwargs `OpenAITicketClassifier.classify`, не затрагивающее `CLASSIFIER_INSTRUCTIONS`, `TicketClassification` и `CLASSIFIER_MODEL_NAME`, replay не заметит. Принимается и документируется. Для Live-прогона это не проблема: Live исполняет реальный `OpenAITicketClassifier`.

### 2.2. Компоненты

* `RecordingClassifier(upstream: TicketClassifier, session)` — вызывает upstream, сохраняет allowlist-представление результата или ошибки, возвращает результат без изменений.
* `ReplayClassifier(recording)` — отдаёт записанный результат; на записанную ошибку бросает `ClassificationError(kind, "recorded classifier failure")` (текст исключения не хранится, как и в WP1).
* Оба — часть существующего слоя `evaluation/`; `FakeClassifier` остаётся upstream для режима `synthetic_recording`.
* `LLMSession` расширяется полем `classifier`; Runner берёт классификатор из сессии, а не конструирует `FakeClassifier` сам. Это единственное изменение Runner.

### 2.3. Единый формат записи (schema_version 2)

Одна запись на сценарий, **общая упорядоченная последовательность** вызовов обоих типов:

```text
Recording v2
  schema_version=2, recording_id, scenario_id, model, source, data_class, status, integrity
  interactions[]:
    sequence            1..n без пропусков (общая для обоих видов)
    kind                "classification" | "llm_response"
    request_fingerprint
    response            (форма зависит от kind)
```

`classification.response`: `type: result | error`; при `result` — `classification` (дамп `TicketClassification`), `usage`; при `error` — только `error_kind ∈ {invalid_output, api_error, unexpected_error}` (тексты исключений не хранятся).

`classification` fingerprint (проекция, затем sha256): `v`, `model`, `sha256(CLASSIFIER_INSTRUCTIONS)`, `sha256(canonical_json(TicketClassification.model_json_schema()))`, `sha256(ticket.message)`. Так replay замечает смену инструкций, схемы ответа, модели и входного текста.

Порядок: агент вызывает классификатор до LLM-цикла. Replay сверяет `kind` и `sequence` позиционно, поэтому перестановка/пропуск обнаруживаются тем же механизмом, что и в WP1 (`sequence_mismatch`, `extra_call`, `missing_calls`).

**Версионирование.** v1 → v2 несовместимо (неизвестные поля запрещены). Загрузчик v2 отвергает v1 как `unsupported_schema_version`; 27 синтетических записей перезаписываются командой `synthetic-record` (детерминированно, без сети). Миграции на месте нет.

### 2.4. Fail-closed

Отказ (harness error сценария, исключение из метрик, ненулевой код CI с `--fail-on-mismatch`) в случаях:

* повреждён JSON, дубликаты ключей, неверный `integrity`, неизвестная версия, `status != complete`;
* `kind` не совпал с ожидаемым на позиции; запись содержит `classification`, а у сценария классификатора нет (и наоборот);
* `classification` не проходит `TicketClassification.model_validate` в текущей версии схемы → `incompatible_classification_schema` (**не** исход FAILED агента);
* лишний или недостающий вызов классификатора;
* содержимое не проходит гейт `scan_*` (поля `claimed_reason`, `order_id` — свободный текст, сканируются как любая строка).

Вторая независимая система Evaluation не создаётся: один формат записи, один загрузчик, один Runner, один гейт.

## 3. Live-адаптер и бюджет (WP2-B)

### 3.1. Принцип: внутри Evaluation Harness платный вызов невозможен без трёх разрешений

Все три должны выполняться одновременно; отсутствие любого — отказ **до** создания клиента.

1. **Явный флаг CLI** `--mode live --allow-live` (без `--allow-live` режим не запускается).
2. **Переменная окружения** `SUPPORTOPS_EVAL_LIVE=1` в том же процессе.
3. **Явный бюджет** `--max-cost-usd`, `--max-llm-calls`, `--max-total-tokens` — без значений по умолчанию; значения должны быть положительными и не выше жёстких потолков из кода (§3.3).

Разрешения задаёт один вызывающий, поэтому они защищают от **случайности**, а не от намеренного обхода. Дополнительно Live CLI отказывает при `CI=true`/`GITHUB_ACTIONS` (флага обхода нет).

Дополнительно:

* **Одобренный датасет.** Live принимает только датасет, чей `sha256` входит в версионируемый список одобренных (в коде, меняется только ревью); произвольный `--dataset` в Live отклоняется. Отчёт содержит `dataset_sha256` и `dataset_approved: true`.
* **Легаси-скрипт.** `scripts/eval_classification.py` (вне `src/**`) читает `.env`, использует `OpenAI()` с `max_retries=2` и не имеет бюджета; это независимый платный путь, и утверждение «единственное место» верно только **внутри `evaluation/`**. WP2-B обязан добавить в скрипт минимальный guard: отказ без `SUPPORTOPS_EVAL_LIVE=1` и `--allow-live`, отказ в CI, `max_retries=0`. Если владелец откажется (D-6) — остаточный риск фиксируется в §10.
* Ключ читается **только** из выделенной переменной `SUPPORTOPS_EVAL_OPENAI_API_KEY` (не `OPENAI_API_KEY`, не `.env`), чтобы рабочий ключ приложения не использовался случайно. Ключ не пишется в отчёт, лог, запись и исключения.
* Live-код — отдельный пакет `evaluation/live/`, импортируется лениво только из ветки `--mode live`. Модули записи/воспроизведения его не импортируют (расширение AST-теста WP1).
* Внутри `evaluation/` конструктор `OpenAI(...)` вызывается в **единственном** месте (`evaluation/live/factory.py`), которое задаёт явно `api_key`, фиксированный `base_url`, `organization=None`, `project=None`, `max_retries=0` (переменные SDK `OPENAI_BASE_URL/ORG/PROJECT` игнорируются) и после построения проверяет `client.max_retries == 0` и доступен только через `LiveRunConfig`, который строится после проверки пунктов 1–3. Для тестов фабрика внедряется параметром (`client_factory`); тесты никогда не создают реальный клиент.
* В pytest действует автоматическая защита в **корневом** `tests/conftest.py` (не только `tests/evaluation`): `openai.OpenAI.__init__` и транспорт `httpx` заменены сторожем, который падает; тест, который не помечен `live` и не имеет разрешения, не может сделать платный вызов даже при ошибке. Маркер `live` регистрируется и исключается из стандартного запуска (`pyproject.toml`: `markers`, `addopts = -m "not live"`; файл входит в список WP2-B). Тест конструктора использует spy вместо реального `OpenAI`.
* CLI-режимы `fake`, `replay`, `synthetic-record` ключ не читают и Live-пакет не импортируют (проверяется тестом).

### 3.2. Обёртка клиента

`BudgetedClient` оборачивает **клиент**, а не агента. Это allowlist-обёртка: доступны только `responses.create` и `responses.parse` (без `__getattr__`-проксирования; `with_options`, `with_raw_response`, `stream` → `AttributeError`), плюс атрибуты, которых требует Runner: `responses.calls` (счётчик `create`), `responses.parse_calls`, `responses.inputs`. Следовательно, **все** платные пути проходят один счётчик; обходного пути через классификатор нет.

**Сеть.** В Live `_no_network` заменяется host-scoped allowlist: разрешены соединения **только** транспорта `BudgetedClient` к фиксированному хосту провайдера; разрешённые соединения не увеличивают `network_attempts`. Всё остальное, включая обработчики инструментов, по-прежнему блокируется и даёт `V_NETWORK`. Тест: обработчик инструмента, открывающий сокет в Live, → `V_NETWORK`.

**Исключения обёртки** (`BudgetExhausted`, `RequestBlocked`) — отдельная иерархия, **не** наследующая `OpenAIError`, иначе `OpenAITicketClassifier` замаскирует их под `ClassificationError("api_error")`. Live-`run_dataset` прерывается по `BudgetExhausted` (остальные сценарии `not_run`). Вердикт сценария (`provider_error` против `mismatch`) выводится из **журнала обёртки** (класс исключения SDK и причина), а не из `ClassificationError.kind`.

Порядок для каждого вызова:

1. **Pre-flight запроса:** динамические тексты (`input`, `tool_outputs`, `ticket.message`) проходят гейт `scan_*` (§6.1); статические (`instructions`, `tools`) проверяются один раз при старте и фиксируются хешем (лимиты `scan_value` на длину/глубину к ним не применяются). Нарушение → вызов **не отправляется**, сценарий — harness error `request_blocked`.
2. **Pre-flight бюджета:** `spent + worst_case(call) ≤ limit` по стоимости, токенам и числу вызовов; иначе вызов не отправляется (`budget_exhausted`).
3. Вызов с `max_retries=0` и заданным `timeout`; время измеряется `time.monotonic()` вокруг вызова.
4. **Post-call:** фиксируются `usage`, задержка, класс ошибки провайдера; обновляется счётчик; при превышении лимита после вызова прогон останавливается.

**`worst_case(call)`** (верхняя граница, не оценка по исходящему `input`, который при цепочке `previous_response_id` занижен):

* первый вызов цепочки: `bytes(instructions + tools + input)` как верхняя граница входных токенов (1 токен ≤ 1 байт UTF-8) + `max_output_cap`;
* вызов с `previous_response_id`: `usage.input_tokens + usage.output_tokens` **предыдущего ответа цепочки** (его вывод входит в контекст) + `bytes(новый input)` + `max_output_cap`;
* если у предыдущего ответа нет `usage` — резерв `max_input_cap` модели из таблицы цен;
* тесты: цепочка из `MAX_AGENT_STEPS=10` шагов с растущим контекстом не превышает лимит ни на одном шаге.

Чтобы потолок был **жёстким**, обёртка добавляет к каждому запросу `max_output_tokens=<cap>` (одинаковый для всех моделей, указывается в отчёте как `request_overrides`). Перечень отличий Live-запроса от production-запроса исчерпывается `request_overrides` в отчёте: `max_output_tokens` и подмена `model` (агент: `MODEL_NAME` прошит, подмена `kwargs["model"]` в обёртке; поля CLI `--agent-model` и `--classifier-model` раздельны). Источник истины о модели в отчёте — `response.model` провайдера, а не trace агента (в нём останется `gpt-4.1-mini`). Без `max_output_tokens` стоимость одного вызова не ограничена сверху (решение D-3).

Повторы: `max_retries=0`; ошибки провайдера (429/5xx/timeout) не повторяются автоматически и фиксируются как `provider_error` (§4.4).

### 3.3. Бюджет

| Параметр | Поведение |
|---|---|
| `max_cost_usd` | лимит оценочной стоимости одного прогона |
| `max_llm_calls` | суммарно `create` + `parse`, включая неудачные |
| `max_total_tokens` | `input + output`, по данным провайдера, с резервом на предстоящий вызов |
| Жёсткие потолки в коде | `ABSOLUTE_MAX_COST_USD`, `ABSOLUTE_MAX_CALLS`: CLI может только **снизить** лимит; повышение — изменение кода с ревью (предлагаемые значения — D-4) |
| Fail-closed | при достижении любого лимита следующие вызовы не отправляются; сценарий в процессе — `budget_exhausted`, оставшиеся — `not_run`; отчёт `status: incomplete`, ненулевой код возврата |
| Атомарность сценария | сценарий, прерванный лимитом, исключается из метрик (не считается ошибкой модели) и перечисляется в отчёте |
| Dry-run | `--dry-run` печатает состав прогона и **максимальную** (worst-case) оценку по таблице цен; сети нет; ключ не читается |

**Таблица цен** — версионируемый файл `evaluation/live/pricing.json` (`model`, `input_per_mtok`, `output_per_mtok`, `max_output_cap`, `as_of`). Модель без записи в таблице → отказ до первого вызова (оценить стоимость невозможно). Цены в этом документе намеренно не приводятся: источник истины — файл, а дата актуальности попадает в отчёт.

**Ошибки провайдера и расход.** Два разных случая:

* `provider_error_pre_response` (429, отказ соединения, ошибка до начала генерации): стоимость 0, но вызов **считается** в `max_llm_calls`; `usage_unknown` не срабатывает;
* `provider_error_post_send` (timeout, обрыв после отправки): сервер мог тарифицировать — в расход заносится резерв `worst_case`; `usage_unknown` для политики abort не срабатывает, одиночная ошибка прогон не прерывает.

**Нет usage у успешного ответа.** Нулевая стоимость не подставляется никогда; `usage` с частично отсутствующими полями считается отсутствующим:

* для успешного вызова без `usage` в счётчик заносится pessimistic worst-case (`reserved`), вызов помечается `usage_unknown`;
* по умолчанию первая запись `usage_unknown` останавливает прогон (`--on-missing-usage abort`); альтернатива `continue` допустима только явным флагом, и тогда отчёт содержит `cost_status: incomplete`, а `estimated_cost` публикуется как **верхняя граница**, не как факт;
* `live.token_usage` и `live.estimated_cost` при наличии `usage_unknown` не выводятся без пометки `lower_bound`/`upper_bound` и счётчика таких вызовов.

**Отчёт о расходах** (`cost` в отчёте): `calls` (по видам и по результату), `tokens` (input/output/total, `provider_reported` vs `reserved`), `estimated_cost_usd` (**оценка**: токены × таблица цен; не биллинг провайдера), `reserved_worst_case_usd`, `limits`, `limit_hit`, `price_table_as_of`, `cost_status ∈ {complete, incomplete}`.

### 3.5. Изменения Runner для Live (перечень по пакетам)

* WP2-A: источник отдаёт `classifier`; Runner не конструирует `FakeClassifier` сам.
* WP2-B: `LLMSession.expected_llm_calls: int | None` — для Live `None`, проверка `llm_calls` в `_compare` пропускается (скрипта нет, число шагов модели варьируется); `result.llm_calls` суммирует `create` и `parse` раздельными счётчиками; замена `_no_network` на allowlist (§3.2); остановка `run_dataset` по `BudgetExhausted`.
* WP2-C: ожидания `live.tool_expectation` вместо позиционного сравнения; вердикты атрибуции; отчёт v2.

Других изменений Runner нет; фраза «единственное изменение» в §2.2 относится только к WP2-A.

### 3.4. Когда допустим `model_quality_claim`

`true` только если одновременно: прогон `status: complete`, число Live-пригодных сценариев ≥ 20 и `repeats ≥ 1` (иначе поле называется `run_complete` без претензии на качество), `usage_unknown == 0`, нет сценариев `budget_exhausted`/`not_run`, security-инварианты не нарушены. Иначе `false`, и метрики печатаются с пометкой `partial`. Само значение `true` не означает «модель хорошая» — только «измерение завершено корректно»; интерпретация ограничена §5.4.

## 4. Live-метрики (WP2-C)

### 4.1. Принципы

* **Измеренное ≠ ожидаемое.** Метрика показывает долю наблюдаемых событий; сравнение с `expected` определяет, является ли отклонение ошибкой модели.
* **Ожидаемые `FAILED`/`DEGRADED` не ошибка.** `task_success` считает совпадение исхода с ожидаемым; `degraded_outcome_rate` публикуется как наблюдение в двух срезах (всего / неожиданные).
* **Атрибуция.** Каждый сценарий получает ровно один вердикт: `match` | `mismatch` (отклонение модели от ожидаемого) | `provider_error` | `harness_error` | `budget_exhausted` | `not_run`. Только `mismatch` ухудшает метрики качества. `provider_error` (исключение провайдера, оборачиваемое агентом в FAILED) не приписывается модели и исключается из знаменателей, но считается отдельно (`provider_error_rate`) и **не скрывается**.
* **Применимость к Live.** Сценарии, чья суть — реакция агента на **заскриптованное** поведение fake (сбой провайдера `raise_error`, намеренно невалидный JSON аргументов, tool-fault по сценарию), к реальной модели не воспроизводятся: модель не обязана ошибаться по требованию. Они помечаются `live.eligible=false` с причиной и **исключены** из Live-метрик (но остаются в A/B).
* **Ожидаемая последовательность инструментов.** Позиционное сравнение WP1 строго; реальная модель вправе выбрать допустимую альтернативу. Для Live сценарий несёт опциональный `live.tool_expectation`: `required` (обязательные вызовы, порядок не важен), `allowed_extra` (допустимые доп. read-only вызовы), `forbidden`. Отсутствует — сценарий не входит в `tool_selection`/`argument_validity` Live (а не сравнивается позиционно).
* **Скоринг детерминирован и правило-ориентирован.** LLM-as-judge не используется (это второй платный путь и канал утечки данных). `answer_contains` в Live допустим только для фактов из данных инструмента; свободные формулировки модели не оцениваются.
* **Нет данных → `null`, не 0 и не 1.** Пустой знаменатель = «не применимо».

### 4.2. Определения метрик

Обозначения: *E* — Live-пригодные сценарии, выполненные до конца, без `provider_error`/`harness_error`/`budget_exhausted`.

| Метрика | Что измеряет | Источник | Формула | Знаменатель | Исключения | Нет данных |
|---|---|---|---|---|---|---|
| `live.classification_accuracy` | совпадение классификации реального классификатора с `expected.classification` | `ClassificationResult` из trace (классификатор вызван реальной моделью) | сценарии, где все заданные поля совпали / знаменатель | *E* с непустым `expected.classification` | `eligible=false`; ошибка провайдера классификатора → `provider_error` (не «неверно») | `null`; нужен минимум n (см. §4.3) |
| `live.tool_selection_accuracy` | выбор инструментов по `tool_expectation` | trace + spy `execute_function_call` | сценарии, где все `required` выполнены, нет `forbidden`, лишние ⊆ `allowed_extra` / знаменатель | *E* с `tool_expectation` | без `tool_expectation` | `null` |
| `live.argument_validity_rate` | (а) **валидность**: доля вызовов с `validation_status=valid`; (б) **верность**: доля вызовов, чьи аргументы совпали с `expected.arguments` там, где они заданы | trace, `run_args` | (а) valid / все вызовы; (б) совпали / вызовы с заданными аргументами | (а) все вызовы в *E*; (б) вызовы с ожидаемыми аргументами | две подметрики публикуются раздельно | `null` по каждой |
| `live.task_success_rate` | исход == ожидаемому и выполнены проверки результата | как `task_success` WP1 | успешные / знаменатель | *E* с `expected.outcome` | ожидаемые FAILED/DEGRADED — успех **только** при совпадении | `null` |
| `live.security_violation_rate` | доля сценариев с нарушением хотя бы одного из 9 инвариантов | `check_invariants` | нарушения / все **выполненные** (включая `mismatch`) | выполненные сценарии, **включая** исключённые из других метрик | не исключается ничего, кроме `not_run` | `null` |
| `live.degraded_outcome_rate` | доля сценариев с наблюдаемым `DEGRADED` | `run.summary()["degraded"]` | наблюдаемые / знаменатель; отдельно `unexpected_degraded` = DEGRADED при `expected.outcome != DEGRADED` | *E* | `provider_error` | `null` |
| `live.latency` | задержка вызовов провайдера (**не** сквозная задержка продукта) | `BudgetedClient`, `time.monotonic()` вокруг вызова | p50/p95/max по вызовам; сумма по сценарию | успешные вызовы | вызовы с ошибкой считаются отдельно (`error_latency`); p95 публикуется только при n ≥ 20 вызовов, иначе `insufficient_data` | `null` |
| `live.token_usage` | токены input/output/total | `usage` провайдера | суммы; среднее на сценарий | вызовы с `usage` | `usage_unknown` — счётчик и пометка `lower_bound` | `null` |
| `live.estimated_cost` | оценка стоимости | токены × `pricing.json` | сумма по вызовам; на сценарий | вызовы с известными токенами и ценой | `usage_unknown` → верхняя граница (§3.3); модель вне таблицы → прогон не стартует | `null`, не 0 |

Дополнительно публикуются счётчики покрытия: `eligible_total`, `executed`, `provider_error`, `harness_error`, `budget_exhausted`, `not_run`, `excluded_by_reason`. Метрика без указания покрытия не публикуется.

**Security-нарушения — не «метрика, которую можно улучшить», а гейт.** Любое нарушение инварианта делает вердикт прогона `FAIL` независимо от остальных чисел; в сравнении моделей (§5) такая модель не может быть объявлена лучшей.

### 4.3. Недетерминизм и неопределённость

* `--repeats k` (по умолчанию 1; для сравнения моделей ≥ 3): каждый сценарий выполняется k раз, учитывается бюджет на все k.
* Сценарий-уровневый результат: доля успешных повторов; повторы **одного** сценария не независимы, поэтому интервалы считаются по сценариям (Wilson 95% для долей, bootstrap по сценариям для непрерывных величин).
* Пример масштаба: 20 из 20 сценариев успешны → нижняя граница 95% интервала Wilson ≈ 0,84. Утверждение «качество ≥ 95%» на таком наборе **не подтверждается**. В отчёт включается `ci95` для каждой доли и предупреждение `small_sample` при n < 30.

### 4.4. Ошибки провайдера

`429`, `5xx`, timeout, отказ по content policy — это `provider_error` (с кодом класса, без текста). Они не повторяются автоматически (§3.2). Ошибки среды (429, 5xx, обрыв соединения) исключаются из знаменателей. Ошибки **природы модели** — усечение по `max_output_tokens`, content policy, превышение длины контекста — относятся к `mismatch`, а не к `provider_error` (иначе метрики завышаются у моделей, которые чаще отказывают). `provider_error_rate` = сценарии с ошибкой среды / выполняемые сценарии; значение выше порога (10%) даёт `status: unreliable` и `model_quality_claim=false`. Метрики публикуются в двух вариантах: с исключением и «ошибка среды = неудача» (sensitivity). Порядок присвоения вердикта: `budget_exhausted/not_run` → `harness_error` → `provider_error` (по журналу обёртки) → `match|mismatch`; нарушения безопасности учитываются **для всех выполненных**, включая прерванные лимитом после первого вызова (одно правило для §3.3 и §4.2).

## 5. Сравнение моделей (WP2-D)

### 5.1. Форма

`compare` — **анализатор готовых Live-отчётов** (модели запускаются раздельными прогонами; общий план запусков и «чередование порядка» не применяются, вместо этого фиксируются время запуска и `response.model`), а не второй Runner: каждая модель запускается тем же Runner (`--model X`) отдельно, со своим бюджетом. Это исключает запуск нескольких платных прогонов одной командой «по ошибке».

### 5.2. Ключ сопоставимости

Отчёты сравнимы только при полном совпадении: `dataset_sha256`, множество Live-пригодных сценариев, версия SDK, commit агента (`src/**`), роли моделей (агент/классификатор), параметры сэмплирования и reasoning, фактический `response.model`,  `sha256` схем инструментов, `sha256(CLASSIFIER_INSTRUCTIONS)` и инструкций агента, версия критериев метрик, `request_overrides` (`max_output_tokens` и др.), `repeats`. `price_table_as_of` в ключ **не входит**: стоимость пересчитывается при `compare` по одной таблице. Единый `max_output_tokens` может занижать reasoning-модели (reasoning-токены расходуют тот же лимит) — такой случай помечается `truncation_rate`, и модель получает `inconclusive`, а не «слабее». Несовпадение — отказ с перечислением различий (не «приблизительное сравнение»).

### 5.3. Что учитывается

| Аспект | Правило |
|---|---|
| Качество | парные сравнения по одним и тем же сценариям. Результат сценария при `repeats>1` бинаризуется правилом «успех, если успешны **все** повторы» (доля повторов публикуется отдельно); точный критерий Макнемара + интервал разности по дискордантным парам; парный bootstrap по сценариям (агрегат сценария) для задержки и стоимости, фиксированный seed; поправка Холма на число метрик; реализация — собственная, без новых зависимостей; только полные пары (сценарий, исключённый у одной модели из-за `provider_error`, исключается у обеих; число пар публикуется) |
| Стоимость | в USD по одной версии таблицы цен; публикуется отдельно от качества |
| Latency | распределения p50/p95 с n; сетевой шум и время суток — ограничение, порядок запуска моделей чередуется по фиксированному seed и фиксируется в отчёте |
| Tool calling | различия (параллельные вызовы, формат аргументов, неподдерживаемый tool calling) → статус `incompatible` для модели, а не нулевой балл |
| Провайдерские ошибки | `provider_error_rate` каждой модели рядом с качеством; ненадёжный прогон (`unreliable`) в сравнение не допускается |
| Недетерминизм | `repeats ≥ 3` обязателен для утверждений о различии |
| Безопасность | модель с security-нарушением не может получить вердикт «лучше» ни по одной метрике |

### 5.4. Допустимые вердикты

Единого рейтинга и композитного score нет. По каждой метрике — один из: `no_significant_difference`, `inconclusive`, `A_better`, `B_better`. Различие вердиктов: `no_significant_difference` — выполнены все пороги достаточности данных, интервал содержит 0; `inconclusive` — пороги не выполнены (мало сценариев/повторов, `unreliable`, усечение) либо интервал слишком широк. Вердикт `*_better` допускается только если одновременно: число Live-пригодных сценариев ≥ порога `N_min` (предлагается 100), `repeats ≥ 3`, доверительный интервал парной разности не содержит 0, нарушений безопасности нет, прогоны `complete`. На текущем датасете (27 сценариев, из них Live-пригодных меньше) результат по построению — `inconclusive`; это ожидаемо и документируется в отчёте. Отчёт сравнения содержит таблицу «качество / стоимость / задержка» без выбора победителя.

### 5.5. Границы

Первая версия: только модели, доступные через Responses API провайдера, под который написан агент (`openai` SDK). Другие провайдеры (OpenAI-совместимые `base_url`, иные API) — вне WP2 (решение D-5).

## 6. Защита данных

### 6.1. Контракт Live Evaluation (первый этап)

**Разрешено:** только сценарии с `synthetic: true` и `live.eligible=true`; датасет прошёл review.

**Запрещено:**

* production-данные клиентов; реальные credentials; реальные персональные данные;
* запись сырых запросов и сырых ответов провайдера (формат записи — allowlist, как в WP1);
* автоматическая отправка данных во внешние сервисы оценки, телеметрию, LLM-as-judge, облачные дашборды;
* чтение ключа из `.env`/общего окружения (§3.1).

**Механизмы:**

1. **Request pre-flight gate.** Перед отправкой каждый исходящий текст проходит `scan_text`/`scan_value`; нарушение — запрос не отправляется. Гейт — вторая линия защиты, не доказательство отсутствия ПД; первая — `synthetic: true` и review датасета.
2. **Запись Live-ответов (`--record-live`) в WP2 не реализуется** (отнесено к будущему этапу); при её появлении ответы модели обязаны пройти тот же гейт; нарушение → запись не создаётся, сценарий помечается. Модель может «выдумать» email/телефон. Для `responses.parse` классификатора дополнительно допустимо `store=False` как override (цепочки нет) — решение D-10.
3. **Отчёты** не содержат текстов сообщений и ответов, только метаданные, счётчики и коды (как в WP1); fail-closed проверка утечки канареек сохраняется.
4. **Retention у провайдера.** Цепочка `previous_response_id` требует хранения ответов провайдером; поэтому единственная гарантия — отправляются только синтетические данные. Это ограничение фиксируется в отчёте (`provider_retention: "enabled_by_agent_design"`).

### 6.2. Будущий механизм работы с реальными данными (не реализуется)

Только отдельным Story при условии: правовое основание и договор обработки с провайдером; обезличивание проверенным пайплайном (токенизация идентификаторов, удаление свободного текста), а не регулярными выражениями; класс данных `customer_deidentified` с подписанным артефактом одобрения; шифрованное хранилище с TTL и журналом доступа; запрет записи сырья; запуск только вручную в изолированной среде, никогда в CI; рассмотрение локальной/self-hosted модели. Дизайн этого механизма — вне EVAL-M02.

* **Scope:** `evaluation/live/` (конфигурация, `BudgetedClient`, фабрика клиента, таблица цен, pre-flight, dry-run), CLI `--mode live --allow-live`, сторож в `conftest`.
* **Файлы:** новые `evaluation/live/{__init__,config,budget,client,factory,preflight}.py`, `pyproject.toml`, `scripts/eval_classification.py` (guard),, `evaluation/live/pricing.json`; изменяемые: `evaluation/runner.py` (ветка режима), `evaluation/sources.py` (`LiveSource`), `tests/evaluation/conftest.py`, документация.
* **Тесты (без сети и без ключа):** провайдер-двойник с управляемыми `usage`/ошибками/задержкой; три разрешения (отсутствие любого → отказ до фабрики); `max_retries=0` проверяется на конструкторе; лимиты cost/calls/tokens (pre- и post-call); отсутствие `usage` → резерв, не 0; модель вне таблицы → отказ; потолок в коде не повышается CLI; request pre-flight блокирует PII/секрет **до** вызова; `parse` и `create` делят один счётчик; сторож pytest ловит попытку создать реальный клиент; Live-пакет не импортируется в режимах fake/replay.
* **Acceptance:** ни один тест не создаёт реальный клиент; dry-run показывает worst-case; при исчерпании бюджета прогон `incomplete` с ненулевым кодом; отчёт о расходах содержит actual/estimated/reserved.
* **Security Risks:** случайный платный вызов (три замка + сторож); утечка ключа (выделенная переменная, редакция); скрытые повторы SDK (`max_retries=0`); обход бюджета через классификатор (клиент-обёртка общая); `max_output_tokens` меняет поведение модели (маркируется как override).
* **Зависимости:** WP2-A; **решение владельца D-4 (потолки бюджета) — блокирующее**; правка `pyproject.toml` (маркер `live`, `addopts`) и guard в `scripts/eval_classification.py`.
* **STOP CONDITION:** все тесты зелёные без сети и ключа; **ни одного реального вызова**. Первый реальный запуск — отдельное действие по явному решению владельца с заданным лимитом.

### WP2-C — Live Evaluation Metrics

* **Scope:** отчёт v2 (`evaluation_class`, `recording_origin`, пространства `logic.*`/`live.*`), `live`-спецификация сценария (`eligible`, `tool_expectation`), вердикты атрибуции, 9 метрик, доверительные интервалы, покрытие.
* **Файлы:** `evaluation/schemas.py`, `metrics.py`, `runner.py`, `datasets/support_cases.json` (миграция `live`), документация.
* **Тесты:** формулы и знаменатели каждой метрики на синтетических `ScenarioResult`; ожидаемые FAILED/DEGRADED не штрафуются; `provider_error` исключается и считается отдельно; пустой знаменатель → `null`; `usage_unknown` → границы, не 0; p95 только при n ≥ 20; Wilson-интервалы; отчёты разных классов не принимаются; значения шести метрик WP1 в `logic.*` не изменились.
* **Acceptance:** отчёт явно говорит, что измерено; Replay-отчёт не содержит `live.*` и не заявляет качество модели.
* **Security Risks:** подмена смысла метрик (разделение имён); утечка текстов в отчёт (fail-closed проверка сохраняется).
* **Зависимости:** WP2-B.
* **STOP CONDITION:** метрики проверены на двойнике провайдера; реальных вызовов нет.

### WP2-D — Model Comparison

* **Scope:** анализатор `compare` готовых Live-отчётов: ключ сопоставимости, парная статистика, вердикты, таблица «качество / стоимость / latency».
* **Файлы:** `evaluation/compare.py`, тесты, документация.
* **Тесты:** отказ при несовпадении ключа; смешение классов отклоняется; Макнемар/bootstrap на искусственных данных с известным ответом; малая выборка → `inconclusive`; модель с нарушением безопасности не получает `*_better`; `unreliable` не допускается; `incompatible` не равно нулю.
* **Acceptance:** на текущем датасете (недостаточно данных) вердикт по каждой метрике строго `inconclusive`; победитель не объявляется.
* **Security Risks:** «лучшая модель» из недостаточных данных.
* **Зависимости:** WP2-C.
* **STOP CONDITION:** статистика верифицирована на синтетике; реальных вызовов нет.

## 10. Остаточные риски

* Текущий датасет мал: Live-метрики будут иметь широкие доверительные интервалы; сравнение моделей даст `inconclusive`.
* Оценка стоимости — оценка по таблице цен, а не биллинг; таблица может устареть (контролируется `as_of`).
* Дрейф внутренних kwargs `OpenAITicketClassifier` replay не обнаружит (вариант (a)).
* Легаси-скрипт `scripts/eval_classification.py` до внедрения guard остаётся платным путём вне harness.
* Провайдер хранит ответы из-за `previous_response_id`; защита — только синтетика.
* `max_output_tokens` и `max_retries=0` отличают Live-запрос от production-запроса; влияние на качество не оценено.
* Недетерминизм моделей и дрейф версий моделей у провайдера: результаты сравнимы только в пределах времени прогона.

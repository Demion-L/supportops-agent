# STC-совместимость и границы экосистемы Latysh Development (Deliverable H)

**Дата:** 2026-11-27 · **Статус:** исследование. В репозитории **нет** кода, схем или документов STC, KAIROS, AGORA, FEMIDA, SYMPOSIUM, SPHYNX [Ф — отсутствие подтверждено поиском по `docs/`, `src/`, `.monolith/`]. Всё о них ниже опирается **только на описание из директивы** и помечено [Н] там, где требует знаний об этих проектах.

Единственный артефакт экосистемы в репозитории с реальным содержанием — MONOLITH (`.monolith/`, CLI) и изолированный эксперимент Agent Commons (ветка `experiment/agent-commons-exp-001`, stdlib, 72 теста), идейно близкий к SYMPOSIUM — **связь не установлена и не предполагается**.

## 1. HERMES как исполнитель конфигураций STC

### 1.1 Разделение ответственности (из директивы) — оценка

| STC | HERMES | Замечание |
|---|---|---|
| Business Composition, Visual Configuration, Capability Selection, Workflow Definition, Configuration Validation | Execution, Orchestration, Authorization, State, Capability Invocation, Outcome Production | Разделение логично и совпадает с границей «конфигурация ≠ полномочия» |

### 1.2 Критическое требование безопасности [В, уверенность высокая]

**Конфигурация STC — недоверенный вход для HERMES в части полномочий.** STC выбирает *желаемые* возможности; HERMES должен авторизовать их собственным доверенным путём (tenant-конфигурация, одобренная оператором/владельцем tenant). Иначе тот, кто сможет подделать или подменить файл конфигурации, расширит полномочия модулей — это ровно тот класс уязвимостей, который Gate предотвращает для LLM. Следствия:

- Конфигурация подписывается/версионируется и **активируется** шагом на стороне HERMES, а не читается «на лету».
- Валидация схемы дублируется на стороне HERMES (fail-closed): неизвестный тип возможности, неизвестное поле, выход за бюджет → отказ.
- STC не получает права вызывать Gate, только поставляет декларацию.

### 1.3 Что в HERMES пригодно для исполнения конфигураций сегодня

| Нужное для STC | Есть? | Основание |
|---|---|---|
| Реестр возможностей по tenant | **Нет** (E) | реестр глобален |
| Типизированные контракты возможностей | Частично (Tool-схемы Pydantic, L0) | `tool_definitions.py` |
| Версионируемая tenant-конфигурация | **Нет** (E) | нет таблицы tenants/config |
| Fail-closed валидация | Паттерн есть (`ServiceSettings`, route audit) | `config.py`, `route_audit.py` |
| Декларативный workflow | **Нет** (E) | порядок определяет LLM |
| Детерминированный исполнитель workflow | **Нет** (E) | — |
| Идемпотентное исполнение шагов | Схема есть, кода нет | `runs.attempt` |

### 1.4 Нужно ли декларативное описание процессов

**Для детерминированных частей — да; для динамических решений — нет.** Предлагаемое разделение [Г]:

- *Заранее заданный workflow* (STC описывает): порядок шагов, условия переходов, обязательные проверки (например, «suppression-check перед send», «срочность — по регламенту»), точки участия человека, бюджеты.
- *Динамическое решение* (LLM внутри шага): классификация, формулирование вопроса клиенту, разбор неструктурированного текста. LLM выбирает **значения внутри** шага, а не **набор шагов** и не **полномочия**.

Минимальная декларация шага: `{id, capability, input_map, on_success, on_failure, requires_human?, budget}` — конечный автомат, а не язык программирования. Нельзя вводить Turing-полные выражения (источник неконтролируемых побочных эффектов).

### 1.5 Контракт STC ↔ HERMES (набросок, для обсуждения) [Г]

`TenantBlueprint v1` — документ: `tenant_ref`, `capabilities[]` (id, версия контракта, конфиг), `workflows[]`, `policies[]` (ссылки на детерминированные политики), `channels[]`, `budgets`. Передаётся **как данные** (файл/запись), не как вызов кода. Версия схемы — обязательное поле; несовместимая версия → отказ активации.

### 1.5а Владение контрактами и доверие активации (по ревью)

`TenantBlueprint` и `OutcomeRecord` — **односторонние предложения HERMES**; контрактом владеет потребитель (STC, AGORA). Не решено: кто доверенный активатор (оператор платформы или владелец tenant), откат версий, TOCTOU между валидацией и применением, секреты — только ссылки, лимит размера/сложности workflow (DoS), антиэскалация (tenant не включает capability сверх тарифа/политики оператора). Подпись не решает вопроса «кто вправе подписать».

### 1.6 Что решение владельца запрещает и это соблюдено

Никакой runtime-зависимости между STC и HERMES не создано и не предложена; контракт описан как формат данных, который владелец может принять, изменить или отвергнуть.

### 1.7 Вывод

Гипотеза «HERMES как исполнитель STC» **не подтверждена и не опровергнута** [Н]: у HERMES нет обязательных предпосылок (per-tenant реестр, версионируемая конфигурация, workflow-исполнитель). Они совпадают с тем, что нужно и без STC, поэтому их проектирование **не создаёт зависимости от STC**, но делает совместимость возможной. Решение о контракте — только после появления самого STC (иначе проектируем контракт к невидимому клиенту).

## 2. Границы ответственности проектов экосистемы

| Проект | Роль (директива) | Граница с HERMES | Риск нарушения самостоятельности |
|---|---|---|---|
| **MONOLITH** | процесс и governance разработки | Не runtime и не зависимость HERMES. Сегодня `.monolith/` и `package.json` (devDependency CLI) лежат **в одном репозитории** — это организационное соседство, не зависимость; код `src/` не импортирует MONOLITH | Смешение «память разработки» и «состояние runtime»; roadmap уже фиксирует: *MONOLITH Durable State не строится внутрь Python runtime* |
| **SPHYNX** | поиск коммерческих возможностей | Поставляет гипотезы спроса (AI Dispatcher), не код | Нет |
| **STC** | визуальная композиция | Поставляет декларации; HERMES исполняет и авторизует (см. §1) | Подмена полномочий конфигурацией |
| **KAIROS** | бронирования | Внешняя система за портом; независимый API | HERMES не хранит его состояние, не импортирует его код |
| **AGORA** | outcome-ориентированная наблюдаемость | HERMES **эмитирует** `OutcomeRecord`/события; AGORA агрегирует и показывает | Встраивание дашбордов в HERMES |
| **FEMIDA** | независимая оценка по человеческим критериям | Принимает доказательства (trace, outcome) и выдаёт вердикт; **HERMES не оценивает себя** и не управляет исполнением по её вердикту автоматически без решения человека | Обратная связь «оценка → исполнение» нарушает принцип «Harness измеряет, не управляет» |
| **SYMPOSIUM** | обмен проверенным опытом | Потребитель/поставщик знаний через явный интерфейс | Агентные знания как доверенная инструкция: опыт — **данные**, не полномочия (в эксперименте Agent Commons эта угроза разобрана в `threat-model.md`) |

### Принципы границ [В]

1. Связь между проектами — **данные и контракты**, не общий процесс и не импорт кода.
2. Любая входящая из другого проекта конфигурация, знание или вердикт — недоверенные данные до валидации на стороне получателя.
3. Каждый проект версионирует свои контракты независимо; несовместимость → отказ, а не «лучшее усилие».
4. Ни один проект не получает полномочий через другой: авторизация локальна.
5. Единого runtime «для всех» нет; HERMES не разворачивает чужие проекты внутри себя.

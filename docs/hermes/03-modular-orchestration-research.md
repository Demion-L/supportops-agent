## 1. Capability Modules

### 1.1 Что есть [Ф]

Единица возможности сегодня — `ToolDefinition` (`tool_definitions.py:54`): имя, описание, Pydantic-аргументы, handler, `has_side_effects`, `requires_approval`, флаги trusted binding. Исполняет её `execute_tool_call` после Authorization Gate. Всё остальное (классификация, политика возвратов, ответ) — зашитые этапы конвейера `SupportAgent`, а не подключаемые единицы.

### 1.2 Предлагаемая минимальная модель [Г]

Не новый фреймворк, а **декларативный контракт поверх существующих кирпичей**:

| Уровень | Что это | Есть ли сегодня | Нужно ли сейчас |
|---|---|---|---|
| L0 Tool | детерминированная операция с типизированными аргументами | да | — |
| L1 Capability | именованный пакет: набор Tool + (опц.) политика + (опц.) промпт-контекст + требуемые scopes/bindings; декларируется в коде, регистрируется статически | нет | **да, для эксперимента** |
| L2 Discovery/Lifecycle | динамическая загрузка, версии, зависимости, hot-swap | нет | **нет**, пока не доказана необходимость |

Типы из директивы укладываются так [В]:

| Тип | Как выражается без нового механизма |
|---|---|
| Deterministic Tool | L0 как есть |
| Integration Module | Tool(ы) + клиент внешней системы + tenant-credentials; **самое слабое место** (см. 2.3, 4) |
| Business Policy Module | детерминированная функция вида `RefundPolicyEngine`; паттерн «LLM предлагает → политика решает» уже реализован |
| Knowledge Module | read-only Tool (поиск) либо контекст в developer-сообщении; tenant-scoped хранилище отсутствует (E) |
| Workflow Module | **нет аналога** (E): сегодня последовательность определяет LLM |
| Specialized AI Agent | Tool, чей handler запускает вложенный прогон (нужны: параметризуемый конвейер, делегирование полномочий, лимит рекурсии — всё E) |
| Human Task Module | **нет аналога** (E) |

**Один модуль — несколько бизнес-возможностей.** Пример Email: `receive` (inbound событие, не Tool — это *вход*), `send` (Tool, side effect, идемпотентность по `message_key`), `reply_in_thread` (Tool + threading), `handle_delivery_event` (inbound событие), `suppression` (детерминированная политика, обязательна перед `send`), `sending_policy` (квоты/окна). Вывод [В]: модуль = набор **входов**, **инструментов** и **политик**, а не один Tool; поэтому L1 должен допускать три вида элементов. Интеллектуальный разбор переписки — отдельный модуль-агент, **не** часть Email-модуля.

### 1.3 Нужны ли заявленные механизмы

| Механизм | Вывод | Обоснование |
|---|---|---|
| Capability Contract | Да, минимальный (id, версия схемы, вход/выход, класс побочного эффекта, scopes, ключ идемпотентности, таймаут) | Без него нельзя ни проверить tenant-композицию, ни тестировать модуль независимо |
| Capability Registry | Да, статический, **на tenant** (см. §2) | Сейчас реестр глобален — несовместимо с «разные tenants — разные наборы» |
| Discovery | Нет | Статического списка достаточно, пока модули пишет сам Latysh Development |
| Module Lifecycle / Dependency / Version Compatibility | Отложить | Нужны при сторонних модулях; преждевременно |
| Failure Isolation | Частично, дёшево: таймаут + перехват в Executor (перехват уже есть: `execution_failed` без текста исключения) | Изоляция процессом — позже |
| Module Configuration | Да, per tenant (см. §2) | Ядро требования |
| Inter-module Communication | Только через оркестратор и типизированные результаты; прямых вызовов модуль→модуль нет | Сохраняет единую точку авторизации |

## 2. Мультитенантная композиция

### 2.1 Главный вопрос директивы

> Может ли существующая модель `TenantContext` и Authorization Gate безопасно исполнять модули без существенного изменения архитектуры?

**Ответ [В, уверенность средняя-высокая]: механизм — да, подключение — нет, оно отсутствует и является основной работой.**

Доказательства [Ф]:

1. `TenantContext` (`interfaces.py`) — идентичность **HTTP-вызывающего** со scopes эндпойнтов (`tickets:write`…). `ExecutionContext` (`authorization.py:63`) — полномочия **агента** (`agent_id`, `allowed_tools`). Это два разных объекта без связи; `grep -ri tenant src/supportops_agent` → 0.
2. Данные инструментов — глобальные словари (`mock_data.py`); `create_support_case` пишет в глобальный `CASES` (`tools.py:203`). Любой tenant сегодня видел бы данные любого другого, если бы ядро подключили к API как есть.
3. Реестр инструментов глобален (`tool_definitions.py:140`), `allowed_tools` — константа (`authorization.py:119`).

Что **переносимо после доработки** [В] (не «без изменений»: Gate не знает tenant, trusted binding хранит один `customer_id`, а не пару `(tenant, customer)`): deny-by-default, независимость решения от LLM, trusted binding после `model_dump()`, закрытые reason codes, sanitization — всё это **не знает о домене** и годится для любых модулей.

### 2.2 Минимальный набор изменений, чтобы вопрос стал «да» [Г — подлежит эксперименту]

| # | Изменение | Тип |
|---|---|---|
| 1 | Доверенный конструктор `ExecutionContext` из `TenantContext` + tenant-конфигурации (по образцу `build_tenant_context`, с аналогичным статическим тестом «создаётся только здесь») | новый код, малый |
| 2 | `tenant_id` и `enabled_capabilities` в `ExecutionContext` (frozen, `extra="forbid"` → добавление полей совместимо) | малое |
| 3 | `allowed_tools` вычисляется как `⋃ tools(enabled_capabilities) ∩ scopes` на стороне приложения, а не константой | малое |
| 4 | Реестр инструментов как параметр `execute_tool_call` / `SupportAgent`, а не глобальный | малое–среднее |
| 5 | Порт данных per tenant вместо `mock_data` (`OrderDataPort` из дизайна API-003 §3, TB6) | среднее |
| 6 | Тесты изоляции: tenant A не видит и не изменяет данные B через любой инструмент; чужой = несуществующий | обязательны |

### 2.4 Требование «модуль не получает полномочий из решения LLM»

Уже обеспечено для инструментов [Ф]. Для композиции нужно сохранить как **инвариант**: `enabled_capabilities` и `allowed_tools` вычисляются только из доверенной конфигурации; LLM может *выбрать из* разрешённого, но не *расширить* набор. Рекомендуется закрепить статическим тестом (как для `TenantContext`) и сценарием Evaluation Harness (инвариант «unauthorized_tool_executed» уже есть в ветке eval-001).

## 3. Оркестрация и делегирование

### 3.1 Разница, зафиксированная кодом [Ф]

Сегодняшний цикл — **один LLM выбирает вызовы инструментов, до 10 шагов, последовательно** (`agent.py:642-664`, цикл по `function_calls`). Это не оркестрация независимых бизнес-возможностей: нет плана вне головы модели, нет разных исполнителей, нет сохранённого состояния между запусками.

### 3.2 Девять сценариев директивы

| # | Сценарий | Статус | Как достичь | Класс |
|---|---|---|---|---|
| 1 | Детерминированный инструмент | **Есть** | — | A |
| 2 | Внешняя интеграция | Частично | Tool-handler; но нет таймаута, retry-политики, tenant-credentials, идемпотентности внешнего эффекта | C/E |
| 3 | Специализированный агент | Нет | Tool, запускающий вложенный прогон (новый экземпляр на прогон уже правило); нужны параметризуемый конвейер, делегированные полномочия, лимит рекурсии | C/E |
| 4 | Последовательность модулей | Эмулируется LLM | Детерминированный workflow-исполнитель (E) либо оставить решение за LLM (недетерминированно) | E |
| 5 | Параллельные независимые операции | Нет | `execute_function_calls` обрабатывает вызовы по очереди (`agent.py:465+`) | E |
| 6 | Передача результата между модулями | Только через контекст LLM | Типизированный data-flow (E) | E |
| 7 | Пауза для решения человека | Нет | `APPROVAL_REQUIRED` — тупик: канала одобрения нет; статусы run: accepted/running/completed/failed | E |
| 8 | Продолжение с доп. информацией | Нет | состояние хранится в памяти и на стороне провайдера (`previous_response_id`) | E |
| 9 | Восстановление после частичного отказа | Частично | сбой инструмента — структурированная ошибка в LLM; схема `runs` имеет lease/fencing/`max_attempts`, **кода нет**; автоматический replay бизнес-операций запрещён до решения идемпотентности (API-003 §13) | E |

### 3.3 Ключевая архитектурная развилка [Г]

Для длительных диалогов (сценарии 7–8) есть два пути:

- **Путь I — пауза/возобновление одного прогона** (durable execution): требует сериализуемого состояния цикла, журнала шагов, переносимости контекста LLM (сейчас он у провайдера). Это «настоящий» движок, дорогой и рискованный.
- **Путь II — событийные короткие прогоны над состоянием в БД** [рекомендуется проверить первым]: бизнес-сущность (заявка) имеет **детерминированный конечный автомат** в PostgreSQL; каждое входящее событие (письмо, ответ клиента, решение оператора) запускает короткий прогон, который читает состояние, делает шаг и записывает новое. Ожидание недостающей информации — **состояние сущности** («ожидает уточнения»), а не приостановленный процесс.

Путь II использует существующие **идеи**: короткий прогон с жёсткими границами, lease/fencing, tenant-scoped репозитории, идемпотентность по ключу события. **Но не существующую схему** (по ревью): `runs.UNIQUE(ticket_id)`, иммутабельные `tickets` и неизменяемые терминальные `runs` не допускают сущность с автоматом состояний и несколько прогонов на сущность — нужны новые таблицы сущностей, журнал событий и привязка `runs` к `event_id`. Отсутствие нового orchestration framework — **гипотеза [Г]**, не вывод. Ограничение: логика состояния пишется в доменных модулях, а не «получается из коробки». Уверенность в выборе: низкая–средняя [Н — нужен эксперимент HX-1]. Известные слабые места (ревью): гонки событий одной сущности (нужна версия/CAS или сериализация); доменные автоматы пишутся заново для каждого домена и не покрываются декларацией без исполнителя; таймеры («ждём ответ 24 ч») требуют планировщика; переходы нельзя выводить из недоверенного текста без детерминированного guard допустимых переходов; история диалога между прогонами хранится в БД (политика ПД), `previous_response_id` для этого не годится.

### 3.4 Делегированная авторизация, бюджеты, рекурсия [Г]

- Правило ослабления (attenuation): контекст вложенного вызова = пересечение с контекстом родителя; расширить его вложенный агент не может. Реализуется методом `derive()` над frozen `ExecutionContext`.
- Бюджеты (токены, шаги, время, стоимость) принадлежат родителю и делятся; сегодня есть только `MAX_AGENT_STEPS`.
- Лимит глубины/числа вложенных агентов — обязательная константа конфигурации (сейчас нет вложенности).
- Таймаут и отмена: отсутствуют вовсе (G9 в API-003); нужны до подключения любых внешних интеграций.
- Побочные эффекты: флаг `has_side_effects` есть, но **Gate его не использует** («side effect alone does not require approval»). Нужен классификатор эффектов: `none | reversible | irreversible | external-communication`, привязанный к политике одобрения.
- Идемпотентность: единственный пример — `create_support_case` через `sha256(ticket_id + reason)`; API-003 §13 фиксирует, что `reason` формулирует LLM → ключ нестабилен. Для HERMES нужны **стабильные операционные идентификаторы**, задаваемые оркестратором.

### 3.5 Нужен ли новый orchestration framework

**Нет оснований утверждать, что нужен [Г — не доказано, а лишь не опровергнуто].** Сначала путь II на существующем ядре. Внешний фреймворк (README Epoch I упоминает LangGraph как возможный выбор — **в коде не используется**, зависимости нет) рассматривается только если эксперимент покажет, что конечных автоматов в БД недостаточно.

## 4. Каналы ввода/вывода

### 4.1 Состояние [Ф]

Единственный вход — демо-скрипт `run_agent.py` и (в работе) `GET /v1/tickets/{id}`; единственный выход — возвращаемая строка. Кода каналов нет.

### 4.2 Предлагаемое разделение [Г]

`Inbound adapter → нормализованное InboundEvent → оркестратор → результат → Outbound adapter`.

`InboundEvent` минимум: `tenant_id` (определяется **адаптером из конфигурации канала**, не из содержимого), `channel`, `external_event_id` (ключ идемпотентности), `sender` + **уровень верификации**, `payload`. Бизнес-операция получает `InboundEvent`, а не письмо/HTTP-запрос.

### 4.3 Ключевой риск безопасности, обнаруженный в ходе исследования [В, уверенность высокая]

Инвариант Epoch I: «`ticket.customer_id` — подтверждённая идентичность; приложение обязано получить её из аутентифицированной сессии» (docstring `SupportAgent.__init__`). Для API-ключа tenant это выполнимо (tenant — авторитет для своих клиентов, API-003 §3.2). **Для email — нет:** заголовок `From` подделываем; SPF/DKIM/DMARC подтверждают домен отправителя, но не личность клиента в бизнес-системе tenant.

Следствие: недопустимо превращать адрес отправителя в `trusted_customer_id`. Нужна градация доверия канала, влияющая на Gate:

| Уровень | Источник | Допустимое |
|---|---|---|
| `authenticated` | API-ключ tenant + `customer_id` от бэкенда tenant | как сегодня |
| `channel_verified` | email с выровненным DKIM/DMARC и сопоставлением адреса с реестром клиента tenant | чтение несекретного статуса; без раскрытия ПД и без необратимых действий |
| `unverified` | остальное | только общие ответы и создание заявки с пометкой |

Это прямо связано с открытым решением владельца по `POST /v1/tickets` (источник `customer_id`).

### 4.4 Сценарий письма → заявка → исполнитель → подтверждение

Какие компоненты есть: аутентификация tenant, idempotency, tenant-scoped хранилище, детерминированный gate. Чего нет: Email in/out, Property Registry, Maintenance Requests, Contractor Routing, Notification, Human Escalation, конечный автомат заявки. Из 7 звеньев цепочки **ни одно не реализовано**; общая основа (безопасность, хранилище) — есть.

## 4.5 Дополнительные угрозы (по независимому ревью)

| Угроза | Мера, которую нужно спроектировать |
|---|---|
| Косвенная prompt injection через тело письма и поля реестра (confused deputy) | Недоверенный текст — только как данные; guard допустимых переходов; корпус инъекций в оценке |
| Коллизия `customer_id` между tenants | Идентичность — всегда `(tenant_id, customer_id)` |
| Fencing защищает строку `runs`, но не внешний эффект: retry после смерти воркера пошлёт письмо дважды | Fencing-токен и стабильный ключ эффекта во внешних вызовах |
| Повтор прогона даёт другой вывод LLM при том же ключе | Ключ эффекта задаёт оркестратор, не LLM |
| Lost update при конкурентных событиях сущности | Версия сущности (CAS) / сериализация |
| Данные tenant уходят провайдеру LLM (`previous_response_id`) | Retention, DPA, только синтетика до compliance review |
| Attenuation только по инструментам не ограничивает **объекты** дочернего агента | Объектные ограничения (tenant/сущность) в производном контексте |
| Noisy neighbor: общие лимиты провайдера, бюджеты per tenant | Квоты и учёт per tenant |
| Право на удаление данных tenant при иммутабельном `tickets` | Политика retention/erasure до первого реального tenant |

## 5. Outcome-Driven Execution

### 5.1 Что измеряется сегодня [Ф]

`AgentRun.summary()`: статус, длительность, `llm_calls`, `tool_calls`, `failed_tool_calls`, `total_tokens`, `degraded`. Evaluation Harness (ветка eval-001) считает метрики **по ожидаемому исходу сценария**, а не по числу действий; `task_success_rate` засчитывает FAILED/DEGRADED успехом только если они были ожидаемы.

### 5.2 Что отсутствует [Ф]

Стоимость (нет таблицы цен/валюты), внешние ресурсы, участие человека, переработка, привязка прогона к бизнес-исходу, агрегация по tenant/модулю.

### 5.3 Предлагаемая запись исхода [Г]

`OutcomeRecord { tenant_id, workflow/capability, outcome_class (resolved | degraded | escalated | failed | abandoned), success: bool|None, evidence_ref, cost { tokens_in, tokens_out, llm_usd, external_usd }, wall_ms, human_minutes, rework_count, policy_violations }`.

Производные: Cost / Time / Tokens per Successful Outcome, Failed Execution Cost. Главная трудность [В]: **определение «успешного исхода» — доменное и принадлежит человеку** (заявка закрыта без повторного обращения? исполнитель принял?). Без оракула метрики измеряют активность, против чего директива. Это совпадает с ролью FEMIDA («критерии определяет человек») и AGORA; HERMES должен лишь **эмитировать** факты, а не оценивать себя.

### 5.4 Переиспользование Evaluation Harness

Подходит [В]: инварианты безопасности (в т.ч. «модуль не вызвал неразрешённый инструмент», «нет сети», «нет утечки секретов»), outcome-ориентированные ожидания, Record/Replay для регрессии логики оркестрации без платных вызовов. Требует: вливания в `main`, отвязки от `SupportAgent` и `Category`, добавления tenant-инвариантов. Правило: Harness **измеряет**, не управляет исполнением (обратная связь в runtime запрещена).

## 2. Trust boundaries

- **Доверенно:** объект тикета, созданный вызывающим кодом (`customer_id`, `ticket_id`); код политики и evaluator, внедряемые при сборке агента.
- **Недоверенно:** текст тикета, аргументы tool-call и вывод LLM (включая заявления «я CEO / администратор»), результат классификатора до валидации.
- Идентичность передаётся в инструменты только исполнителем (`trusted_customer_id`, `trusted_ticket_id`) после `model_dump()` и перекрывает любые значения от модели.
- Решение о возврате принимает детерминированный `RefundPolicyEngine`; `ALLOW` политики ≠ авторизация инструмента и ≠ выполнение.

## 3. Основные инварианты

1. Идентичность никогда не выводится из текста тикета или аргументов модели.
2. Отсутствие/невалидность идентичности = отказ, а не «разрешить по умолчанию».
3. Отказ для чужого и несуществующего объекта побайтно одинаков.
4. Любая ошибка закрывается безопасно; наружу идут только коды из закрытого набора (`SAFE_ERROR_CODES`, `SAFE_DIAGNOSTIC_TYPES`).
5. Trace и `summary()` — только метаданные.
6. Контекст исполнения привязан к run и потоку-владельцу; после завершения run инструменты получают отказ.
7. Authorization Gate и `RefundPolicyEngine` не менялись кампанией (изменения только вызывающего слоя).

## 4. Известные LOW/INFO (приняты владельцем)

- **LOW-1:** враждебный статус evaluator — требует подмены доверенного evaluator; fail-closed сохранён.
- **LOW-2 / техдолг:** `len(tool_result.output or {})` может выбросить `TypeError` при нестандартном типе вывода handler'а. Текущие handlers возвращают `dict`. Не исправлено в WP4; исправить при появлении внешних/плагинных handlers.
- **LOW:** `reason_code` в `TOOL_EXECUTION` пишется только вместе с `diagnostic_type`; allowlist причин политики нужно синхронизировать при добавлении новых кодов.
- Прочие LOW/INFO из security-handoff WP1–WP3 сохранены без изменений.

## 5. Ограничения модели безопасности

- Защита in-process; один процесс, одно доверенное окружение. Нет аутентификации вызывающего, нет мультитенантности, нет персистентного хранилища (`mock_data`).
- Ответ LLM (свободный текст) не гарантирует отсутствие данных, которые модель уже получила в контексте: гарантия касается того, что модель *получает* от инструментов, а не того, что она *скажет* (см. `test_characterization_final_answer_is_llm_text_not_guaranteed`). Текст, передаваемый модели, не очищается.
- Один экземпляр `SupportAgent` не предназначен для параллельных запросов; параллелизм — через отдельные экземпляры.
- Защита от prompt-injection — через архитектуру (модель не владеет идентичностью), а не через фильтрацию текста.

## 6. Требования к будущему API

- Идентичность клиента и tenant определяются **только** по проверенным credential на стороне сервера; никогда из тела запроса, заголовков, произвольных claim'ов или текста тикета.
- API строит доверенный `Ticket`/контекст сам и передаёт его агенту; клиент не задаёт `customer_id`/`ticket_id` для авторизации.
- Область (scope) credential ограничивает допустимые операции до вызова агента.
- Ошибки API — единый безопасный формат; чужой и несуществующий объект неразличимы (включая коды и тайминги по возможности).
- Один запрос — один экземпляр агента (или строго сериализованный доступ); состояние run не разделяется между запросами.
- Логи/трейсы API подчиняются тому же metadata-only правилу.

## 7. Что нельзя нарушать при PostgreSQL и multi-tenancy

- Tenant-фильтр применяется на уровне доступа к данным (каждый запрос к БД параметризован tenant и владельцем), а не только в слое инструментов; рассмотреть RLS как вторую линию обороны.
- Идентификаторы объектов не глобально-доверенные: проверка владения = `(tenant_id, customer_id, object_id)`.
- «Не найдено» и «чужой» остаются неразличимыми, в т.ч. на уровне SQL-ошибок и сообщений драйвера (текст ошибок БД не попадает в trace/ответы — инвариант 4).
- Ключи, `ticket_id` и `case_id` генерируются/привязываются сервером; `create_support_case` остаётся привязанным к доверенному тикету того же tenant.
- Соединение/сессия с tenant-контекстом не разделяется между потоками/запросами (пул соединений — сброс контекста при возврате).
- Миграции не должны ослаблять ограничения владения; кросс-tenant тесты обязательны для каждого нового запроса.
- Не писать содержимое тикетов, PII и ответы БД в trace (инвариант 5).
